# Native environment migration toward v1 parity

## Scope and acceptance

The developer requested full environment parity for the existing v1 configuration, not empty app entries or shell wrappers around `docker compose`. The inventory is the user's `CONFIG_DIR/migration-report.json`; it is machine-local data, not checked into this repository. The initial migration contains 25 applications, 9 libraries, and six enabled targets. Forty-one explicit source entries remain blocked, including a broken v1 Dockerfile symlink. Automatically discovered repository targets are additional scope, not included in that count.

Full parity requires preserving profiles/defaults, build inputs, dependencies and readiness, service-specific environments and credentials, network reachability, persistence and lifecycle, run/build/test results, diagnostics, and usable configuration migration. Every item must be backed by public-boundary evidence. Parsing a document alone is not functional parity. Actual existing apps, real providers/models, credentials, clusters and engine workloads are not acceptance fixtures and must not be started or restarted without separate authorization.

## Implementation sequence

1. **Service-level execution configuration (implemented).** Native Compose source accepts `x-secret-refs`, `shm_size`, `extra_hosts` and bounded exec-form health probes. All service references resolve before any engine effects, freeze for the run and stay scoped to the declaring service. Stack-wide longest-first redaction protects logs, including overlapping sibling secrets. Native container creation receives the approved shared-memory bytes and host mappings. Invalid references, literal/reference collisions, invalid hosts and oversized memory fail closed. No existing source is automatically rewritten.
2. **Persistent resources (not implemented).** Add native named-volume declarations with explicit lifetime/persistence and resource identity. Creation, attachment, detach, retention, name collision, interrupted create and cleanup failure must be receipt-fenced. Never adopt or remove v1/external volumes by name/labels, silently substitute temporary storage, or delete database data at task completion. Persistence needs durable identity/reopen behavior and a separate explicit data-transfer operation if existing v1 database contents are to be carried over.
3. **Restart lifecycle (not implemented).** Represent restart policies in approval and native observation. A restarting container is not an exited owner; cancellation still drains/stops only the original receipt-fenced generation. Handle exhaustion, host shutdown/reopen and uncertain mutations without phantom lease release. Do not simply pass `--restart always` while retaining the current one-creation/no-restart assumptions.
4. **Shared infrastructure and application prerequisites (not implemented).** Extend the repository-bound infrastructure model deliberately to support global services and the frontend/backend cross-repository dependency. Keep exact repository/owner authorization, atomic acquisition, collision detection, independent task workspaces, prerequisite readiness, reference-counted release and diagnostic leases. No attaching to a legacy network or an unrelated workflow's running app.
5. **Configuration-owned sources and build contexts (not implemented).** Capture immutable source bundles from config, bind all includes/templates/scripts to approval, and materialize safe task-local build inputs without requiring untracked files in each checkout. Preserve existing checkout changes. Implement credential-reference templates and safe build-secret transport without storing credential bytes in configuration, approval, transcript or image layers. Refuse missing inputs rather than guessing. Account for v1's broken Dockerfile symlink and repository-specific missing `.npmrc`/template inputs.
6. **Compose conversion and target discovery (not implemented).** Convert existing includes, short-form ports/commands/environment arrays, profiles and defaults into the native model; service names remain network aliases, not adoption authority. Support bounded, explicit environment interpolation by reference without evaluating shell source. Preserve daemon socket selection, endpoint/query declarations and telemetry encoding/attribution. Discover only supported repository build/test commands as inert candidates; never execute discovery automatically.
7. **Finish migration (not implemented).** Preview every source and diagnostic, apply only the exact validated bundle, preserve references instead of copying secrets, refuse overwrite/stale inputs, and allow idempotent retry/rollback. Update the machine-local inventory only after each target is actually supported. A full migration must report no unresolved target except a specific missing/invalid user input; empty app entries are not success.

## Implemented service schema

```yaml
services:
  web:
    image: example:local
    x-secret-refs:
      APPLICATION_PASSWORD: APPLICATION_PASSWORD_ENV
    shm_size: 512m
    extra_hosts:
      host.docker.internal: host-gateway
    healthcheck:
      test: [CMD, probe, --ready]
```

References resolve from `CONFIG_DIR/.env` or the launching process, just like target `secretRefs`. The extension is intentionally explicit: arbitrary `${...}` interpolation remains refused. Service references cannot be overridden by service literals or conflicting target mappings. Target-wide references retain their existing semantics; only service-specific references gain isolation. HTTP/query credential bindings remain target-level, not a new service diagnostic authentication API.

`shm_size` accepts integer bytes or integral b/k/m/g strings, at most 8 GiB. Container definitions expose `shmSize` in bytes and `extraHosts` as a hostname-to-IP/`host-gateway` map. Exec health probes are translated to `exec` with individually POSIX-quoted words, not concatenated shell source; argument substitution and metacharacters remain literal. Existing string and CMD-SHELL probes retain their explicit shell semantics. Disable-plus-health settings still fail closed.

## Evidence and limits

`test/compose-diagnostics.test.ts` exercises native public task tools against a disposable synthetic engine: exact approval snapshots contain reference names but no values, service-only `--env` bindings, shared-memory/host/probe argv, missing-later-service refusal before network creation, and cancellation after credential-file removal. Existing credential rotation, diagnostic ownership, network replacement and SQL lifecycle tests remain applicable. `test/compose-subset-fences.test.ts` exercises authenticated staging/check/candidate/materialization refusal for unsupported or malformed inputs. No renderer/helper/unit-parser tests are used as execution evidence.

This first implementation does **not** make the 41 blocked definitions runnable, migrate volumes/data, change the live user configuration, or establish real Docker/Podman/Windows parity. The remaining steps above are implementation work, not authorization already granted to execute those environments.

## Native execution expansion (supersedes the corresponding initial statuses)

Implemented persistent/ephemeral named-volume lifetimes, engine restart policies, config-captured Compose and Dockerfile sources, native Compose shorthand compilation, BuildKit secret mounts with encoded reference templates/file references, and HTTP(S) URL readiness for shell runs. These are native capabilities with public-boundary evidence, not a declaration that the user migration is finished.

### Volumes and restart ownership

A top-level `volumes` entry supports only the local driver: `{}` means persistent, `x-lifetime: ephemeral` opts into deletion after confirmed container cleanup, and an explicit `x-scope` names a native exclusive data scope across definitions. Without that extension scopes are app/volume-specific. New volumes receive random names/nonces. Persistent creation receipts store the host/scope/name/nonce/creation-time tuple privately under the native state directory and are included in each fresh approval that requests reuse. No discovered volume is adopted. Reuse fails if the stored receipt changes between approval and execution, or if engine creation metadata is missing or differs. Native per-scope locks serialize attachment and remain quarantined after ambiguous creation or host death; there is no stale-PID/age takeover. Engine volume APIs have no immutable volume ID or conditional mutation: metadata-perfect hostile replacement is outside the assurance provided by creation-time/nonce checks. Actual engine/data-application verification remains separate. Lifecycle cleanup never deletes persistent data, including after failed startup. Legacy volumes/data are not imported.

`restart` supports `no`, `always`, `unless-stopped`, `on-failure`, and bounded `on-failure:N` for N=1..100. Completion prerequisites and build/test containers cannot restart. Restart backoff is an unavailable diagnostic observation, not an exited owner: its live lease is retained, startup remains time-bounded, and stop addresses only the same receipt-fenced container before removal. A host restart still does not restore container authority.

### Captured inputs and secrets

`compose.source` contains inert captured YAML in the approved configuration; `compose.file` remains the virtual workspace-relative base for bind paths. No config-directory traversal exemption or checkout file installation is needed. The parser accepts a single declared native local bridge, explicit container names (occupied names still refuse), short-form fixed ports/mounts, literal KEY=value environment arrays, hyphenated container environment keys, and shell-quoted command strings compiled to argv without shell evaluation. External volumes/networks, implicit inheritance, arbitrary effects and `${...}` interpolation remain refused. Included source files must still be converted/captured as a complete closure by the migration; runtime include discovery has not been added.

`container.dockerfileSource` is materialized to a private native scratch file only for an approved build and removed before publishing its exit. `container.buildSecrets` maps BuildKit IDs to either `{env: "DECLARED_SECRET_KEY"}`, `{file: "/explicit/absolute/private/file"}`, or `{template: "...", encoding: "xml"|"text", refs: {PLACEHOLDER: "DECLARED_SECRET_KEY"}}`. Environment and template inputs must refer to target `secretRefs`, never literal environment mappings. File inputs are bounded regular UTF-8 files opened without following leaf symlinks or hard links, read only after approval. Runtime values travel solely in private CLI environment variables referenced by `--secret id=...,env=...`; no secret context file, build argument, serialized plan or credential copy into a checkout is generated. XML placeholders are escaped; redaction includes rendered values and credential-file assignments. As with all approved Dockerfiles, this is not a sandbox against malicious instructions deliberately copying secret mounts into layers. Migrated Dockerfiles must use secret mounts at every credential-consuming RUN; a parser acceptance alone cannot establish that conversion.

Shell `readyUrl` is a literal IP-loopback HTTP(S) run URL, mutually exclusive with `readyText`. A startup-only port availability check refuses pre-existing listeners before spawning the child. Readiness polls are bounded, do not follow redirects, require a successful HTTP status and continuing child survival, and never adopt an existing server. There is no atomic port-bind transfer to arbitrary commands; this is not OS isolation. Explicit URL ports participate in batch/runtime collision checks. Endpoint/query authority remains tied to the native live lease.

### Verification and remaining inventory

108 tests / 711 assertions pass in bounded groups: Compose/source/readiness 51/283, container 50/345, core/operator 7/83. New fixtures prove restart retention and original-ID cancellation, persistent receipt reuse across independent approvals, ephemeral cleanup, lost-receipt quarantine, replacement-volume refusal, native shorthand from captured YAML without repository source files, XML/file BuildKit transport with secret digests and redacted deliberate fixture leaks, and owned-shell URL readiness/refusal of occupied listeners. Synthetic engines do not prove physical Docker/Podman behavior or database durability.

The initial 41 blocked explicit sources are not the complete v1 discovered target inventory: read-only discovery also finds repository build/test/run targets, two Helm-based run targets, and a system-shell rendering of the frontend script. The discovery inventory contains 108 rows: 16 Docker builds, 25 Docker runs, 27 shell builds, 26 shell tests, 11 shell runs, two Kubernetes/Helm runs, and one system-shell run. The broken misspelled Dockerfile symlink is not a discovered runnable target. Library/app entries with no target remain genuinely empty, not invented commands.

Still required before declaring full migration: complete include/definition conversion and exact publication, global infrastructure/network and application prerequisite semantics, native container telemetry transport/attribution, repository target/default/profile discovery parity, Helm target support or an explicitly agreed scope decision, conversion of legacy credential-consuming Dockerfile RUN instructions, and resolution of missing user credential references/input files. Several EFIX/EIV references are absent from both exported process variables and the v1 `.env`; a migration must report their names without inventing values, copying credentials, or pretending those targets are executable. No live user configuration or existing workload has been changed by this execution expansion.

## Installation-sized offline conversion checkpoint

`bun scripts/preview-environment-migration.ts --source-config <v1-config> --source-tree <explicit-symlink-root> --current-config <v2-config> --socket <explicit-native-engine-socket> --npmrc-reference <private-file-reference> --output <new-private-directory>` is an **inert preview**, not publication or execution. The source-tree and npmrc options are optional; the engine socket is explicit and is never contacted. Existing output is refused. `--apply` is refused; native exact-digest developer publication remains required.

The converter imports no v1 runtime/discovery code, runs no discovered commands, reads no `.env` or npm credential bytes, modifies no checkout, and preserves current targets/defaults. It records source SHA256/byte manifests and the live-definition base digest. Explicit symlink roots, regular-file/64-KiB source limits, bounded include closures, duplicate/override refusals and native compilation apply. Includes become config-captured Compose sources. This is not a claim that per-acquisition networks replace v1 global shared-network semantics.

Dockerfiles are config-captured. Maven settings use reference-only XML-escaped BuildKit templates; **each** later Maven RUN mounts the secret again. npm consumes an explicit private file reference, with each npm ci/install RUN mounting it; no credential file enters the build context. Known Redis password arguments and MySQL root-password health probes become explicit quoted environment-reference transports, never copied literal credentials. Generated V2_* references require operator input; they are not silently populated from legacy literals. Unknown credential/embedded interpolation forms remain refused. A schema-valid candidate does not prove that dependencies, credential inputs, engine images or applications are available.

The machine-local preview at `/tmp/v2-environment-migration-preview-c566001-c` contains 34 projects, 46 targets, 40 converted candidates, four preserved script-source entries and 12 explicitly blocked source entries. It does not change `~/.config/agentic-coding-v2`. The 12 source blockers include global infrastructure mapping, frontend script dependency conversion, the grid backend telemetry interpolation and a broken legacy Dockerfile link. Repository-discovered shell targets, profiles/default discovery, cross-repository acquisition and Helm targets remain additional scope beyond this explicit source inventory. **Full parity is not achieved or archived by this checkpoint.**

Definition staging/preflight/candidate/publication now share a 256-KiB definition limit and 64-project/256-target bounds, enough for this installation. Individual auxiliary/public sources remain limited to 64 KiB, and the 16-member atomic execution limit is unchanged. Captured Compose candidates compile directly from approved definition data, without requiring or publishing a repository source overlay. An accompanying repository overlay for the same captured source remains refused.
