# Backend migration acceptance checkpoint

This is the current open-work index. `environment-parity.md` is chronological evidence: its early tables and historical “next” notes are not a current completion checklist. No score, subset or fake-backed fixture proves full legacy or live parity. Backend completion precedes adapting the existing TUI; do not expand the web UI or change the general UI/pi-durable session contract.

## Current supported boundaries

- Native task ownership, exact-plan approvals, atomic acquisition, cancellation/cleanup barriers and uncertain-resource quarantine; no saved process/container/Pod adoption.
- POSIX shell, owned Docker/Podman, strict Compose subset and explicit existing-cluster bare Pods. Provider-time container/Compose and single-pod logs; single-replica loopback forwards.
- Explicit lifetimes (independent, referenced, shared) for agent-owned roots and declared same-repository prerequisites on shell, Docker/Podman and Compose run targets; a shared prerequisite is reused only under its exact approved plan. Attached shared roots diagnose their reused prerequisites (SQL today, HTTP through the same approved-closure scope) with exact plan identity, same owner/task only and no fallback to another root. Kubernetes resources, foreign/shared external infrastructure and cross-owner sharing are not admitted.
- Retained live waits preserve position across bounded calls. Restart marks history interrupted. Explicit recovery requires fresh current-plan approval and a new acquisition, never an old ordinal or execution authority.
- Held-shell, owned health-ready Docker/Podman, explicit Compose-service and owned single-replica Pod HTTP/HTTPS; container endpoints require an exact declared published TCP loopback binding and Pod endpoints the run's own declared loopback port forward. PostgreSQL admission supports shell, owned health-ready Docker/Podman, explicit Compose-service and owned single-replica Pod infrastructure. Live read-only execution is proven over shell and owned health-ready container targets (frozen credentials, redaction, rotation, write refusal) against a disposable PGlite server; the container engine itself remains fixture-synthesized. Every diagnostic path re-observes container creation identity/running state/health, bounded to two seconds, before authority-sensitive dispatch/publication; a Compose call also re-observes every original sibling service and the owned network ID. Native-issued HTTP/SQL receipts never restore network or execution authority.
- Private revision-fenced JSON/Compose/auxiliary staging, bounded literal env_file resolution from exact staged bytes, candidate/tree digests, explicit retention/reuse/release, and configuration-only promotion. Source roles/path collisions are fenced. Nested auxiliary retain/reuse/reopen/release has public coverage.
- Read-only discovery at the root or one explicit nested public directory, inside the authorized checkout or captured native workspace. No recursive enumeration or automatic project selection.

## Next retained-tree implementation boundary

`drafts.ts` now commits assembly admission before invoking filesystem materialization. The intent uses existing bounded, revision-fenced cleanup-attempt history/acknowledgement with kind `assemble`. It records the exact request, draft revision/content/tree identities, prior retained name and deterministic exclusive temporary name. Completion retires the assembly marker in the transaction recording the result or beginning supersession deletion. Historical completed requests replay reports; pending or acknowledged attempts never replay effects under the original identity.

Disposable authenticated API scenarios kill the host after rename and before completion for both first creation and supersession. Reopen discloses a pending assembly intent; old and fresh requests are blocked, acknowledgement changes no files and does not permit the old request, explicit digest release removes only the orphan, and a distinct request can then succeed. Previous ownership is preserved. These fixtures inject the kill at the filesystem boundary, not a production failpoint.

Temporary-write interruption is now covered. Retained metadata exposes bounded observations for each assembly intent's temporary name: present with metadata fingerprint/count, absent, or unavailable. `POST /api/environments/drafts/tree/temporary-release` requires requestId, exact acknowledged assembly id/revision, current fingerprint and `remove: true`. It commits a separate deletion intent before dispatch, re-observes before deletion, and records a data-only completion receipt. Replacements/symlinks/stale fingerprints fail closed; completed replay never removes a later occupant. No unknown directory sweep, content import, ownership adoption or execution recovery occurs. Fingerprints now include bounded per-file content digests read through O_NOFOLLOW descriptors with dev/ino/size/mode re-verification, so a same-size rewrite with restored timestamps still changes the fingerprint and refuses the old release identity (disposable SIGKILL/write-interruption plus same-size mutation scenario). Directory deletion re-verifies each directory with lstat before chmod, refuses symlinks, re-checks the root immediately before unlinking and verifies absence afterwards. Unowned `tree-<digest>` staging directories are now disclosed as `unownedTemporary` with their own observations, never deleted here. This narrows TOCTOU races but remains path-based hardening, not descriptor-relative namespace protection or an OS sandbox; unowned temporary removal has no API delete path. Deletion uncertainty is now proven (`tree-cleanup-uncertainty.test.ts`): when the effect fails or the host dies after the pending cleanup marker commits, the attempt stays pending across reopen, the same request cannot be replayed, new tree assembly is blocked, and explicit acknowledgement retires the blocker without granting retry.

The owned-container diagnostic milestone now closes initial HTTP/HTTPS binding plus fresh container health/identity admission for HTTP and SQL. Docker/Podman HTTPS fixtures verify frozen bearer use/redaction after rotation and cleanup after startup references are removed; HTTP fixtures verify refusal of stale health, copied-label replacement, unknown/slow inspection, cancellation before dispatch and uncertain issuance after in-flight cancellation. SQL fixtures also verify post-preparation unhealthy/replacement/unknown refusal without opening a query issuance. Container observer reads are serialized with the monitor, with independent cancellation budgets, rather than borrowing its lifetime/authority. Existing shell/native HTTP redirect, CA and crash-replay scenarios remain shared proof, not new container-specific SIGKILL or real networking verification.

The Compose diagnostic milestone adds explicit per-endpoint/query service selectors, per-service reference filtering, stack-wide fresh observation of children plus owned network, synchronous `closing` revocation for in-flight diagnostics, and one frozen startup environment snapshot shared by all child services and network commands. Coverage: Docker/Podman HTTPS frozen bearer use after rotation with response `service` disclosure, completion-prerequisite ordering, owned release after reference removal, and refusal without issuance/dispatch for missing/wrong/completion selectors, unhealthy/replaced/stopped siblings, replaced network, offline engine and slow inspection; Compose SQL covers rotation, replaced sibling and issued-cancellation drain. This is synthetic-engine plus separately fixture-owned HTTP/PGlite, not live Compose networking or crash replay for Compose writes.

## Owned-pod endpoint diagnostics over declared loopback forwards

An endpoint declared on a Kubernetes target is admissible only when the target is single-replica and declares exactly one loopback port forward on the endpoint URL's own port; the same rule is applied when the declaration is read, so a mismatched or missing forward never becomes a binding. A Pod endpoint reaches the app through that forward only; the agent never opens a second forward, selects a pod or injects a port.

Each dispatch re-observes through the run's single observation loop: the owned pod's live UID, readiness and running state, plus whether the exact declared forward is still this run's own running process (a forward that exited is not reopened). The observation is queued behind the monitor's own reads rather than issued concurrently, so a diagnostic never competes with the CLI. Endpoint credentials and redaction come from the run's frozen startup environment, exactly as for containers.

`test/kubernetes-diagnostics.test.ts` covers declaration refusals (missing forward, forward on another port, several replicas), a successful GET with the response body through the fixture forward, and refusal with no request reaching the fixture server once the declared forward has exited. The fixture cluster proxies real TCP to a separate fixture HTTP server; it does not prove cluster networking, kubelet behaviour, pod-level readiness semantics or a real `kubectl port-forward`. SQL over an owned pod, shared/external bindings and multi-replica diagnostics remain unsupported.

## Owned-pod SQL over a declared loopback forward

A Kubernetes infrastructure target may now declare a PostgreSQL query connection, under the same exact rule as endpoints: single replica and exactly one declared `portForwards` entry whose `local` port is the connection's own port. The check runs when the definition is read and again at dispatch, so an approved connection cannot be re-described into another port or a second forward.

Each call re-observes, through the run's single observation loop, the owned pod's live UID, running state and readiness, plus whether that exact declared forward is still the run's own running process. An exited forward is a refusal, not a reopened forward; the pod itself is not stopped by that refusal. Credentials come from the run's frozen startup references and are redacted with the same frozen redactor as the container path; the read-only transaction, rollback, row bounds, TLS identity and receipt fences are unchanged.

`test/kubernetes-sql.test.ts` covers the declaration refusals (no forward, forward on another port), a real PGlite PostgreSQL protocol conversation through the fixture forward with `transaction_read_only` on and the stored secret redacted from rows, and refusal at dispatch with no query reaching the database once the declared forward has exited. The fixture is a bounded pod client plus a local TCP proxy and a separately spawned TLS PostgreSQL server; it is not a cluster, kubelet or production database authentication.

## Navigable native telemetry: trace trees, richer span evidence and bounded history

Spans now retain bounded evidence beyond attributes: up to 64 exception/event entries with names, nanosecond times and redacted attributes, up to 64 links with trace/span IDs and redacted attributes, and exporter drop counts for attributes/events/links. Malformed event times or link IDs refuse the whole ingest batch with 400, exactly as malformed spans/logs already did. Events, links and drop counts are retained evidence with truncation, never permission to fetch another run or provider.

`src/environment/telemetry-tree.ts` builds a bounded retained graph per exact trace: original parent IDs are preserved, while traversal cuts cycles, reports `missingParents` (unexported or evicted) and `cycleCuts`, lists `roots`/`children`, and returns parent-before-child, exporter-start-time-ordered nodes with `depth` and `traversalParent`. The accompanying `structure` carries an explicit completeness disclaimer: retained observations only, not complete distributed history.

`TelemetryCollector::query` adds `view: flat | tree` (tree requires an exact trace ID), exact-query opaque cursors (`cursor`, 64 hex chars, five-minute expiry, at most 200 retained), and `spanId`/`http`/`service`/`rootKind` filters. Every observation carries a monotonic sequence; a cursor pins the exact run/query fingerprint plus a high-water mark, so later captures are excluded rather than silently mixed in, and evicted/replaced boundaries refuse with a reload-newest error instead of substituting another span. Output stays inside the existing byte budget, with the tree structure accounted for before records. Trace summaries now also disclose `rootKind`, `rootBasis` (reported-parentless versus fallback), bounded `services`, `eventCount`, `linkCount` and nanosecond-derived `durationMs`; a retained trace with zero filter matches stays retained with an explicit zero-match selection, and the 200-ID eviction window still separates known evictions from unknown trace IDs. The HTTP API and `otel_query` expose the same fields; HTTP matching joins the span name with non-empty HTTP attribute values, so `GET /nested` matches a `GET` method plus `/nested` route without requiring empty attributes to contribute spaces.

`test/telemetry.test.ts` now asserts the tree representation for its single-span trace. `test/telemetry-navigation.test.ts` (36 assertions) proves, through the authenticated API against one disposable shell run: tree paging across cursors with depths/parents/children, missing-parent and cycle evidence, redacted event/link attributes with drop counts, `http`/`service`/`rootKind` trace-summary selection, exact-trace `http`/`rootKind` span selection, span-bound log selection (`spanId` requires `traceId`), newest-first trace paging, log paging that excludes a later capture behind the pinned cursor, cursor/query-mismatch and evicted-boundary refusals, unknown-trace `unknown` availability, malformed-ingest 400 evidence in owned logs, and cursor invalidation after the run stops. The fixture server proxies real OTLP/HTTP JSON over loopback with a synthetic OTLP payload, a separately spawned app process and a local change-triggered late capture; it proves receiver/query/cursor behavior, not SDK, gateway, multi-run or live-provider telemetry.

## Attached shared-root diagnostics over reused prerequisites

An attached shared acquisition approves its prerequisites without starting a second copy, but its live prerequisite generations live in another batch. Same-batch diagnostic closures could not resolve them: `declaredInfrastructure` against the root's own batch throws before any shared fallback, so SQL (and HTTP through the same scope helper) from an attached root failed closed with no fallback. Attached shared lifetimes were therefore half-usable: the store was shared, but only the first batch could query it.

`src/environment/reference-scope.ts` now accepts the exact approved batch plans (`batchApproved` reads the acquired wait receipt for that batch/owner) and resolves the declared closure against those approvals instead of only the live same-batch plans. Every reused generation requires exact `sameApprovedPlan` identity, same owner/task and shared lifetimes on both sides; ambiguity (zero or several live generations) refuses with the existing `"Shared diagnostic prerequisite generation is ambiguous or unavailable"` and `"SQL requires the selected live held application..."` errors, never adoption by app name. The approved-closure path also replaces reference equality with `sameApprovedPlan`, so reopened generations still match. `src/environment/http-manager.ts` and `src/environment/manager.ts` pass the approved plans into `referenceScope`; `src/environment/query-manager.ts` adds a cross-batch branch for a named requiring app in another batch than the shared infrastructure, mapping the full transitive closure to live generations (same-batch preferred, otherwise exactly one live shared generation with exact identity) and checking only the requiring root plus its scope resources, so an unrelated first-batch root exiting does not block the attached query. Same-batch behavior is unchanged, and requiring-app-less SQL still selects from the infrastructure's own batch.

`test/shared-diagnostics.test.ts` proves the milestone through the public API against disposable PGlite: `api` starts shared with `store`, `worker` attaches shared and reuses the one live store (no second copy), `db_query` for `store` with `app: "worker"` approves with `root.run` as the worker generation and `resources` as the single reused store ID, frozen-secret redaction holds, and the store outlives the first root. HTTP uses the same scope helper and is enabled for attached roots through the same approved closure, with SQL as the fixture proof.

## Crash-during-temporary-deletion delete-path guarantees

The temporary-release route commits its deletion intent before dispatch and records completion after, so a host death inside the filesystem removal leaves a pending `temporary-release` marker with an uncertain tree. `test/fixtures/tree-release-interruption.ts` (new) makes that crash deterministic the same way the assembly fixture does: it monkey-patches `fs.rmSync` in a child process and SIGKILLs either before the removal call (tree intact) or after it returns (tree gone). Only the exclusive `tree-<digest>` temporary prefix trips the patch; the retained `trees/` root never matches. `test/tree-release-interruption.test.ts` (new, 2 scenarios, 38 assertions) drives both phases through the authenticated API: interrupt assembly writing, reopen, acknowledge, interrupt the release deletion, reopen. Both phases disclose a pending `temporary-release` attempt, refuse same-request replay (`automatic retry is forbidden`), block fresh assembly, and retire to `acknowledged` without granting retry. Before-removal leaves the tree intact and a fresh request with the re-observed fingerprint completes the deletion; after-removal leaves the tree absent and a fresh request fails closed (`identity changed or is unavailable`) instead of deleting anything else. Both phases end with a fresh assembly succeeding. One genuine protocol behavior surfaced: the deletion walk re-pins directory modes before unlinking, so even a killed attempt changes directory ctimes and invalidates the previously observed fingerprint — the retry must carry the currently observed identity, which the trees metadata discloses. No `src/` change was needed.
