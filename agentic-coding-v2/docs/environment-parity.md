# Environment parity ledger

Reference: the previous host's `docs/agent-environments.md`, `docs/environment-runtime-port.md`, `docs/devenv/cross-runtime-endpoints.md`, agent environment tools, action/default-target resolver, runtime owners and dependency leases. This is a capability ledger, not a claim that implementation or fixture success proves live-runtime parity.

The v2 implementation remains independent. No legacy runtime imports, storage adoption, production deployment, automatic host restart, container takeover, saved-PID cleanup, workflow graph or evidence subsystem is authorized by this work. Task ownership replaces workflow ownership. Profiles remain model selection, not permission.

## Verified checkpoint

Native task scenarios use disposable repositories/state, faux model responses, executable Docker/Podman substitutes and an isolated in-test Unix-socket engine. They exercise approval-before-effects, provider/profile defaults, foreign stop refusal, exact live creation IDs (including replacement with copied labels), unknown daemon occupancy, missing/unhealthy readiness, actual build/test exits, private stdout/stderr metadata, cancellation barriers and daemon-global image writer quarantine across client families, aliases and workspaces. The shell queue scenario also verifies that an unrelated app can pass a blocked conflicting batch without stealing its FIFO priority. Availability checks use only executable/socket filesystem metadata, never CLI invocation, daemon probes or secret resolution. Known-unavailable targets are excluded from implicit fallback; a broken declared default still fails rather than silently selecting another target. Native scenarios also verify newline-free raw shell readiness and that redacted log presentation cannot invent a marker. A SIGKILL/reopen container scenario verifies persisted diagnostic IDs (reset to unknown ownership/health), zero engine invocations during restart/cancellation, quarantined resources and authenticated revision-bound inspection release. Its orphaned log client is bounded to the disposable fixture engine.

An isolated authenticated browser smoke with fixture-only status/log data verified target eligibility/default text, health updates, retained log DOM nodes, unsent chat drafts/focus and no console errors. This was not a live-engine smoke. No live container engine, existing app, credential, cluster or host service was operated on.

Compose native scenarios additionally verify approval-before-effects, compiled source digest fencing, checkout-relative mounts, independent service IDs/status, reverse cleanup, intra-stack port collision refusal before engine calls, partial rollback without stopping a foreign second service, unsupported effect refusal and whole-stack quarantine on daemon loss. Functional shared-mode scenarios cover a fixture web app that can run only when its worker is reachable on the shared network by service alias and has real fixture-engine health, an unavailable prerequisite that prevents readiness, complete stack cleanup, foreign-name refusal, copied-label network replacement refusal, foreign attachment protection, lost-receipt quarantine and private network observations. Tests do not assert compiled-plan ordering or exact networking argv. Native Podman-client scenarios verify that shared mode is metadata-ineligible without any CLI calls and explicitly isolated mode remains usable without silent provider substitution. The SIGKILL/reopen scenario covers both single containers and a shared-network Compose stack; saved network/service IDs remain diagnostics, never adoption authority. No live Compose installation or DNS lookup was exercised; the disposable workload simulation does not prove live DNS compatibility.

The first Kubernetes functional scenario uses a disposable kubectl substitute through a real native task/review. It verifies approval before invocation, an API identity summary without private metadata, no invented reachability on API failure, no invocation after approved source changes, no app lease acquisition and normal temporary-client cleanup. It does not test helper layout or exact argv, use real credentials, contact a cluster, or establish live kubectl/Helm compatibility. Only explicitly configured numeric-loopback HTTPS contexts with reference-only credentials are currently supported. The bare-pod scenario adds native approval-before-effects, API readiness of two pods, configured image/environment delivery, private API output, ordinary cancellation cleanup preserving an unrelated pod, copied-label UID replacement preservation with app quarantine, and app-exit-before-readiness rollback. Its minimal disposable client implements only the public Pod list/create/UID-precondition delete boundary, not a scheduler or fake cluster. No helper-layout or exact-argv assertions were added. The same small scenario now holds API readiness false until both replicas are present, verifies no successful start during that hold, forwards configured HTTP/TCP probe contracts, and observes post-start readiness loss/recovery without killing the app. It controls API status rather than simulating a kubelet, and does not assert internal compiled-plan order. Pod Ready without a readiness probe is not application health; passing probes are not end-to-end business verification. A separate persistent native-host scenario now kills the held Pod host with SIGKILL and reopens its JSONL state. Saved UIDs survive only as diagnostic observations reset to unknown ownership/health. A disposable client invocation journal verifies no client execution during reopen, refused saved-receipt stop, task cancellation or inspected release; the owned synthetic Pod remains present until the fixture operator removes that exact UID while preserving an unrelated Pod. Anonymous release is rejected; authenticated confirmation against the current receipt revision records inspection and releases quarantine without cluster calls. This verifies the native no-adoption recovery boundary, not a live Kubernetes API/host crash, durable cluster history or scheduler behavior. Live kubelet probes, scheduler/network/image-pull behavior, Helm and port forwarding remain unverified/pending.

## Completion rule

Do not label full parity achieved while a row is pending or verification is unavailable. CLI fixtures must exercise real native task/tool approval, executable argv, structured observations, ownership refusal and cleanup; they do not count as Docker/Podman/kind integration smoke. Disposable live-runtime smoke must use only newly created, uniquely labelled resources, be explicitly opted into, and report unavailable runtimes as unverified, never passed. Keep the small behavioral suite rather than adding per-helper tests to inflate coverage.
