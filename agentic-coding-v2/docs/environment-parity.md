## Exact-content configuration promotion

`POST /api/environments/drafts/promote` writes the exact staged configuration document to the live `environments.json` once the developer supplies that content's digest as an explicit approval and the draft's stored revision/digest still match. Preconditions: native v1 schema acceptance within 32 projects / 128 targets, every referenced repository already authorized and present at its real path, destination absent or a regular file (never symlink/directory) of at most 64 KiB, and a destination outside every authorized repository. Identical live bytes short-circuit to `unchanged` with no write.

The replace is an exclusive same-directory temp file (`0600`), fsync, rename and best-effort directory fsync, with the temp file removed on every failure path and a no-follow digest read-back afterwards. The fence compares the destination base recorded with the draft against the live destination immediately before the write, inside a cooperative cross-instance directory lock (`mkdir`-acquired, release attempted on normal exit, no automatic reclaim). That lock serializes cooperating app instances only; it is not an OS lock, so a non-cooperating writer can still lose an update. A failing read-back records nothing and leaves the fence refusing further attempts rather than restoring bytes that could clobber a concurrent writer. Each outcome is kept as immutable promotion history (at most 64, readable by `promotion-…` id, surviving draft deletion) with explicit `sourceFilesWritten`, `repositoriesChanged`, `runtimeChecked` and `reloaded: false` flags; exact retries replay the record without writing.

## Referenced-root lifetime with prerequisite retention

Implemented `env_start`'s second explicit lifetime, **not** a reference registry and **not** a change to default/operator semantics. `referenced-roots-v1` keeps the single exclusive atomic acquisition and its dependency-first startup and rollback, but makes declared shell app roots the stop/expiry units: each root has its own activity clock while a prerequisite has none and is retained by live root references. Validation refuses other runtimes, container/Compose/Kubernetes members, mixed lifetime modes, non-agent ownership and any plan without an app root, before approval and effects. A request cannot upgrade, split or reacquire an already-held coupled batch.

Release reuses the existing dependent-first cleanup barrier with original private handles and adds last-reference release: rounding over the same immutable same-acquisition graph, prerequisites become eligible only once every declared dependent generation is confirmed released, and generations already attempted in an uncertain outcome are never retried by that operation. Direct stop of a still-referenced prerequisite is refused before any effect. A live prerequisite lost outside native control invalidates every root that declared it, dependent-first; an unprovable closure fails closed instead of falling back to siblings or saved identities. The idle lifecycle exposes the referenced scope (`referenced-native-root`, `referenced-prerequisite-closure`, protection `referenced-prerequisite`) and never reaps a prerequisite on its own clock. Exact-root diagnostics identify the requiring root generation. SQL requires that generation plus its declared prerequisites and no longer depends on unreleased siblings; HTTP approvals, receipts and published results and telemetry answers now carry the same `root: {run, resources}` descriptor, revalidated at admission, dispatch and publication, so a closing or replaced prerequisite refuses the operation rather than substituting another run. Default coupled runs gain no descriptor.

Eleven public scenarios in `test/referenced-lifetime.test.ts` cover the shared prerequisite diamond: per-root stop with the prerequisite closure retained, refused direct prerequisite stop, dependent-first last-reference release in observed stop order, immutable stop replay, external loss of the shared prerequisite releasing both roots before its own prerequisite, and a scoped HTTP/telemetry diagnostic naming the exact root and prerequisite generations with a stopped root admitting neither a request nor a substitute generation. They also cover expiry: an in-flight diagnostic keeps its requiring root alive while an idle sibling expires through the native `idle_ttl_minutes` sweep, the retained closure survives, and expiry of the last root releases it dependent-first. A later acquisition is decided against the whole held closure rather than the batch receipt — any running, closing or interrupted generation refuses it, with a reason that separates operator-inspection quarantine from a still-held closure — and the fence opens only after every generation exited, at which point a fresh acquisition restarts the closure dependency-first. A completed referenced HTTP diagnostic also renews the activity clock of the root it belongs to. Owner release closes a referenced acquisition dependent-first with the same retention barrier, leaving no clock or quarantine behind. `shared-prerequisites-v1` adds the one admission extension the earlier slices deferred: a later disjoint acquisition of the same owner attaches to the already-live declared prerequisite generation instead of starting a second copy, decided from live state and revalidated before that generation would have been started, with cleanup released only with the last reference across all acquisitions and prerequisite loss invalidating every live root that declared it — verified by an external loss of the shared prerequisite that releases the roots of both acquisitions before its own prerequisite. ## Verified staged-tree identity at promotion

The isolated tree was assembled, verified and discarded with no connection to promotion, so a draft carrying saved source text could be written to the live configuration without any verified tree ever existing for those bytes. A written promotion record carries that tree digest, count and bytes with `treeRetained: false`.

The identity is re-derived from the staged text by one deterministic function that the disk verification must also match, so the requirement can be checked without keeping a tree, and it still proves neither current source content, a fresh base check, runtime readiness nor a retained directory. The promotion fence, lock, temp-file/fsync/rename path and uncertain-effect handling are unchanged. One public scenario covers the refusal before assembly, the stale identity after an edit, the written promotion carrying the tree digest and the absent staging leftovers.

Retention itself is explicit and separate from the digest identity. An assembly can ask to keep the tree (`retainStagedTree`, refused for candidate validation or an ephemeral tree): the verified tree is moved, still mode-pinned, into one private `trees` directory addressed by its own tree digest, and the receipt records that name. Retention adds no authority — promotion still reads the recorded digest, never the directory, and a retained tree is readable history rather than an execution or publication input. Release is by exact recorded digest only: a superseding verified tree for the same draft, or draft deletion, and nothing is deleted by pattern, by age or by inferred path. An edit that is not followed by another assembly leaves the stale tree in place, visible but owned by that draft's receipt, so no sweep ever decides on its own that a directory is orphaned.

## Provider event time for owned container and Compose service logs

Container log capture now asks Docker/Podman for per-line timestamps (`logs --follow --timestamps --tail 200 <id>`) and keeps that event time instead of substituting host receipt time. The runtime prefix is parsed only at the start of a completed line and stripped from retained output, so model-visible text is unchanged. A provider-timed capture records `observedAt` per completed line; host receipt time is still recorded but is not used for `since` filtering under that basis.

`since` therefore filters by the runtime's own event time for owned containers and for exact Compose service buffers, still before grep and tail. A line whose prefix is missing or unparseable stays untimed: it is never selected by `since` and never borrows a neighbouring line's event time. Aggregate Compose output keeps "not chronological" framing and no timing, because headers and multiple service buffers are interleaved. Kubernetes client diagnostics remain undated.

Clipped service buffers no longer shift event times onto different text. A kept tail must begin on a completed-line boundary and the surviving receipts must account for exactly the retained characters; otherwise the capture reports `not-captured` with no basis rather than a plausible but misaligned time window. A container's timing is also withheld whenever a failure suffix follows the follower output, because that text is not a timed completed line.

New public scenarios cover: `--timestamps` being requested and the prefix being absent from returned output; only the line newer than the requested instant surviving, with older lines counted as excluded; Compose exact-service captures exposing provider event time with aggregate framing unchanged; and a deliberately clipped single-service capture explicitly losing timing while still returning output. Limits: this is not exactly-once or lossless log history, not a clock-skew guarantee, and not proof against a runtime that emits malformed or duplicate prefixes. Timestamps come from the engine's own clock, which may differ from this host's. Only the newest retained 2048 completed records/64k characters are covered, a crash can lose later observations, and no live engine smoke test was possible here — verification uses the disposable fixture engine.
