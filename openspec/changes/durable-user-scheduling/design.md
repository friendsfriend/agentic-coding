## Context
The unified Bun server owns authenticated backend operations and lifecycle (`src/server/lifecycle.ts`, `app.ts`, `client.ts`, `protocol.ts`). The current orchestrator bootstrap lives in `src/tui/orchestrator/session.ts`; it must become a non-TUI boundary usable by the server, retaining a compatibility re-export. Existing workflow starts enter `src/server/operations/observations.ts` and `engine.ts`. Existing `Host.submit` serializes conversation mutations and submits followUp inputs, but the inspected wrapper does not prove durable deduplication across launch/ack crashes. Shell workflow-monitor notes are best-effort and follow the active conversation; neither behavior is sufficient for scheduled delivery.

One cohesive primary change includes backend, all targets and manual UI. No follow-up drafts or reduced backend milestone. Developer approved additive host hooks alongside fix-late-mcp-registration; do not edit the Pi bridge, depend on unmerged code, or narrow imported-tool access/native codemode. Wiki monitoring/subscription concepts are advisory and distinguish best-effort event notes from these durable scheduled inputs.

## Goals / Non-Goals
**Goals:** durable user-managed WHAT/WHEN separation; one validation/service authority; traceable immutable admissions; full manual/tool parity; bounded recovery and honest availability; unchanged human authorization.

Developer clarification (implementation): every broader-than-read-only standalone occurrence requires explicit operator approval before writable activation. The occurrence waits durably in `waiting-review`, retaining its job occupancy; neither an orchestrator nor a stored policy setting can approve it. Read-only defaults remain automatic. Cancellation/pause/edit before activation authority still wins. The shared authenticated API and manual occurrence detail must expose this operator-only approval; scheduling must not create parallel automatic approval or a workflow for standalone work.

**Non-Goals:** OS wake-up, remote hosts, natural-language parser, generic cron/RRULE, dependency DAGs, exactly-once external side effects, automatic approvals or merging. The scheduler operates only while the owning server runs and the machine is awake. Closing a view does not stop it; closing a shell that owns the server does. Headless `agentic-coding server` supports longer availability without inventing a daemon.

## Decisions
### 1. Server service and persistence
Add pure domain/recurrence modules under `src/scheduling/`, schemas in `src/contracts/scheduling.ts`, and adapters/store/service/routes under `src/server/scheduling/`. Register authenticated versioned routes, typed client methods and lifecycle-owned timer/reconciliation resources. Server must not import TUI. Move shared orchestrator bootstrap to `src/agent-host/orchestrator-session.ts`; UI re-exports/delegates. Reuse existing host/runtime/model/policy and workflow admission adapters; no second agent runtime. Workflow-facing I/O follows the Effect guide; pure recurrence and state transitions remain plain TypeScript.

Developer clarification (implementation, scheduler SQLite security): preserve the specified scheduler filename and extend the repository-owned capability-pinned VFS to register the explicitly validated basename per root (`herdr.db` or `scheduling.sqlite` only). Scheduler main files and every reserved sidecar must use held directory/file capabilities, with no pathname SQLite fallback. Reuse private ownership/mode/link checks and cover substitution, locking, supported WAL conversion and hot-journal recovery. Linux native build/runtime validation remains a required pre-merge CI gate, not evidence supplied by macOS checks.

Use a dedicated config-root `scheduling/scheduling.sqlite` (private directory/files) rather than workflow stores or subscription JSON: scheduling spans projects and needs transactional claims. Follow repository SQLite version gates/transactions; install schema v1 on explicit service startup only, reject newer/corrupt stores without overwriting. Snapshot before future destructive upgrades; no speculative compatibility shims. Inject store/clock/target adapters for tests. Cross-store admissions require target-side idempotency, not merely a scheduler mutex.

Tables: jobs (id, revision, name, target discriminator, self-contained task/original instruction, references, project/repository, preset/model references, execution/worktree/base/branch settings, permission/review policy, reporting destination, timestamps/tombstone); schedules (id, revision, jobId, enabled/paused/cancelled, structured timing, timezone, nextDue, late policy, cursor, timestamps/tombstone); occurrences (id, scheduleId/revision, jobId/revision, nominalDue, admittedAt, immutable resolved job/config/identities/destination snapshot, state/reason, claim fence/lease, attempts/nextAttempt, target admission id/run link, processing/completion timestamps); mutation receipts (principal/request key, body digest, result). Store configuration references, never credentials, tokens or copied environment files. Resolve concrete identities/configuration at admission, recording provenance and non-secret effective policy. Edits never rewrite admitted snapshots.

### 2. Timing contract
Structured union: once {at: UTC instant, sourceDelayMs?}; interval {anchor: instant, everyMs: positive integer >= 60000}; calendar {weekdays: distinct ISO weekdays 1..7, hour:0..23, minute:0..59, timezone:IANA}. Daily is all weekdays; weekdays and Mondays cover agreed use cases. No seconds/month rules/cron. Interval is elapsed time anchored to original instant, never completion-relative. Relative delay resolves once using server clock; tools/UI supply explicit timezone for calendar and for displaying a local once selection. Missing/invalid timezone or unresolved local input is rejected rather than guessed. Local once selection requires an offset/fold choice if ambiguous and rejects nonexistent time. Persist UTC plus display zone and creation input provenance.

Calendar recurrence computes local dates in the named zone: spring-gap wall times are skipped (not shifted); autumn fold runs only the earlier instant, once per local date. Use a timezone-aware library if no existing helper supplies these semantics; isolate it behind recurrence.ts and pin dependency/lockfile normally, never patch dependencies. Preview next five instants with local offset, timezone and DST policy; persist cursor and last nominal instant so backward clock steps cannot repeat a slot. Forward clock jumps use downtime rules. Server recomputes preview and next run authoritatively on create/edit; clients do not calculate their own schedule authority.

### 3. Occurrence identity, overlap and misfires
Unique scheduled occurrence key (scheduleId, nominalDue); manual run-now uses (scheduleId, mutation request key). Stable occurrence id is the downstream idempotency key. A transaction checks schedule/job revisions/state, materializes occurrence and obtains a fenced lease. Job-level no-overlap spans all referencing schedules: pending delivery, claimed/admitted/running/waiting-review/unknown-outcome all hold occupancy. A due slot while occupied is recorded skipped-overlap, never an unbounded queue. Wake-ups allow one outstanding per job and at most one scheduled wake-up processing per destination conversation; other due wake-ups are skipped with links to the outstanding record. Run-now honors this policy and paused state unless the user explicitly resumes; cancelled schedules reject it. Run-now does not advance recurring cadence; on a once schedule it consumes the once trigger atomically so it cannot later execute again.

On resume recurring schedules skip every slot strictly before the reconciliation time, record a bounded missed range summary with count/first/last, then advance to the first future slot; no historical jobs are replayed. A slot equal to reconciliation time is eligible once. Timer ticks use persisted cursor and an explicit normal polling allowance of 5 seconds; ordinary tick delay within that allowance is not downtime. One-time wake-ups default run-late without expiry and display lateness. Other once jobs require explicit run-late or expire-after {graceMs >= 0}; beyond grace mark expired, never silently drop. Global fair admission batches <=100 per tick and retry/backoff avoid starvation. Availability and next execution are estimates, not guaranteed deadlines.

### 4. Transactional mutations and recovery
All mutations require client requestId; repeat same principal/key/body returns stored result, changed body conflicts. Updates require expectedRevision (409 conflict on stale); job edits affect future occurrences for every referring schedule and return affected ids. Pause/cancel/delete atomically fence unadmitted claims and suppress pending not-yet-admitted execution; resume recalculates next future recurring slot and applies once late policy. Reschedule/postpone replaces next due, increments revision and records supersession; for recurrence postponement is a single next-run override, subsequent cadence remains anchored. Editing cadence replaces future cursor only. Deleting tombstones the schedule, not its job/running execution/history. Refuse job deletion while live schedules reference it.

Admission linearization: target admission is durable, keyed and queryable before runnable dispatch. Developer clarification (implementation): reserve a durable non-runnable identity/content-pinned target, persist its receipt, then atomically check the scheduling revision/fence and commit immutable `admittedAt` activation authority. That scheduling-store transaction is the admission point. Activate idempotently afterward using the same identity and authority; post-authority failures retain occupancy and reconcile that target, never create a new execution. Pre-authority pause/edit/cancel wins even if a harmless native reservation exists. No SQLite transaction spans remote I/O. Mutations race using a per-occurrence admission authorization/fence: if mutation wins, stale dispatch cannot admit; if durable admission wins, mutation returns already-admitted with target link and does not kill it. Do not hold SQLite transactions across remote I/O. Use durable target reservation/admission receipts plus query/reconcile and a final fenced activation handshake; target must not execute a cancelled reservation. Reservation and activation both idempotent. Persist receipt before activation; recover every intermediate state. Do not release job occupancy on lease expiry or ambiguous transport outcome.

Workflow adapter allocates a stable workflow id from occurrence identity and routes through existing supported start validation (task, repo, app/stage/branch/worktree/preset and review invariants). A repeated start verifies occurrence ownership/digest before returning existing workflow; never attaches to an unrelated same-id workflow. Standalone adapter allocates a tracked isolated run/worktree and durable manifest before invoking existing host ensure/submit lifecycle, with safe read-only default; explicitly selected broader policy uses ordinary authorization/reviews. It has independent output/evidence/run links and is never an orchestrator prompt. Waiting human gates remain active occupancy.

Wake-up adapter pins host identity + conversation id + run association, not current session.json alone. Add a dedicated scheduled-admission verb to host protocol/client: keyed durable receipt, expected conversation, content digest and immutable envelope. It admits only followUp, never steer, and stores the original instruction, why/what to recheck, references, due/late information and reporting destination independently of compaction. Temporary unavailable target retains pending delivery; missing/deleted/rebound destination becomes destination-unavailable attention, not another conversation. Developer can explicitly retarget through a reviewed job edit for a future admission, never silent fallback. `/new` does not redirect old schedules.

At the native conversation boundary, prove requestId deduplication and receipt lookup are durable/atomic with inbox admission; if insufficient, implement an application-owned durable inbox consumption/receipt protocol using supported storage transactions. A separate receipt written before/after submit alone is insufficient. No dependency patches or blind retries across an uncertain submit. Instrument dequeue/processing and turn completion separately; queued/admitted is not success. Restart reattaches to the same run/submission and reconciles terminal outcomes, never launches a fresh occurrence for partially executed work. Local fixture crash tests are a release gate for this protocol.

Retry only transient pre-execution infrastructure/admission failures, same identity, at 1s/5s/30s/120s/300s (five retries). Exhaustion is launch-failed plus attention. Missing destinations retain durable blocked pending state without spinning; availability changes/manual retry can reattempt same occurrence. Agent/workflow failure is terminal execution-failed, not automatically relaunched. Unknown admission outcome stays reconciling/attention until authoritative lookup; it must never be treated as an ordinary launch failure permitting duplicate work.

### 5. Shared API/tools and manual surface
Expose `/api/v1/scheduling/{jobs,schedules,preview,occurrences,status}` reads and explicit POST mutation envelopes for create/update/pause/resume/run-now/postpone/cancel/delete. Operation schemas discriminate target/timing/policy, reject unknown fields, bound prompt (64KiB), names (120), refs (50), list pages (100) and validate target start settings. An atomic create operation can create job+schedule together; separate job management supports reuse. Enforce existing principal policy on every path; scheduling routes added to orchestrator policy do not authorize human-review actions or arbitrary execution beyond existing policy. Revalidate effective authority at admission, refuse deleted presets/configurations rather than substitute defaults. Manual UI and tools call this same service.

Tools: create_job, update_job, list_jobs, create_schedule, update_schedule, list_schedules, schedule_status, schedule_action, schedule_history, preview_schedule. schedule_action is a discriminated action union including postpone/run-now/pause/resume/cancel/delete; job removal is explicit. Confirm id/revision, target, resolved timezone/timing/next run, effective model/execution/review/late/no-overlap policies, reporting destination and shared-job edit impact. Compact paginated results, detailed snapshots opt-in. Orchestrator guidance offers scheduling for later checks; explicit 'remind yourself' creates a wake-up with enough context. Ambiguous recurrence/authority/timezone prompts clarification, never implicit recurring tasks. A recheck is observation/reporting authority, not remediation/deployment authority.

Home navigation gains Schedules list/detail/editor/history under `src/tui/schedules/`, using existing forms, modals, tables and route/destination primitives. List: name, target, project, timing/zone, enabled/paused, next, last result, active occurrence and availability. Editor supports every target and timing, reusable job selection/edit, required target-specific settings, original instruction/context/destination and explicit late policy. Server preview/confirmation is mandatory before save; validation stays inline with retained form input. Revision conflict offers reload, never silent overwrite. Actions include all tool operations; destructive changes require confirmation explaining active-run behavior. Detail shows immutable occurrence policy/status/reason/attempts and opens linked workflow, standalone output/evidence or exact orchestrator transcript; missing destinations explain why navigation is unavailable. Use per-surface keybind catalog, shared footer/help, standard navigation hidden from footer; verify actual footer and '?' modal. Do not put key cheats inside content.

### 6. Status, history and notifications
Distinct states: due/pending, reserved, admitted/queued, processing/running, waiting-review, succeeded, execution-failed, launch-failed, reconciling, destination-unavailable, skipped-overlap, missed, expired, cancelled-before-admission. Paused is a schedule state, not an execution success. Persist target links and transition reasons/timestamps. Publish bounded scheduling events through existing event/attention surfaces with authoritative snapshot/resync on loss; never rely on transient notifications for history or wake-up delivery. Notify on completion/failure/blocked destination and human-review wait; do not route review decisions to scheduled agents.

Retain detailed terminal occurrences for 90 days and at most 1000 per schedule (oldest terminal first); retain compact last-result/aggregate missed counts and deletion audit tombstone for 90 days. Never prune active/unknown records or idempotency keys still needed by an admitted target. Prune terminal payloads/receipts only when target can no longer replay the identity; monotonic cursors and durable tombstones prevent old timers from recreating pruned slots. Paginate history with stable cursors and explicit retention boundary. Bound active jobs/schedules to 1000 each with actionable validation rather than unbounded memory scans.

## Risks / Trade-offs
- Cross-store crash consistency is the principal risk → explicit reservation/activation receipts and fault-injection tests; no claim that a scheduler-side unique row alone solves dispatch.
- Existing host requestId semantics require verification → prove durable admission via local fixtures; fail closed on uncertainty, no speculative dependency patch.
- Host/bridge concurrent edits → approved minimal additive hook boundary; preserve imported tools without allow-lists and native codemode, review merge diff before integration.
- Library timezone data can change → store admitted instant/offset, expose future preview; test named DST fixtures and avoid ad hoc Intl offset arithmetic.
- Standalone tracking is additive product surface → reuse host and lifecycle, require working output navigation, no fake workflow or untracked process.
- Always-on expectations → visible server status and lifecycle docs; no OS daemon/wake promise.
- Wiki descriptions of best-effort monitor delivery must not imply schedule durability → dedicated documentation/wiki step updates the existing concepts, not planning-time wiki edits.

## Migration Plan
Add new config-scoped store at server startup without changing user workflows or host data until explicit scheduled-admission support is needed. Use normal version gates and supported durable document conventions; if host schema changes, follow existing snapshot/restore upgrade policy. Verify fresh/reopen/corrupt/newer stores in isolation. On rollback stop scheduler/server, preserve scheduling DB and any upgraded host snapshot/WAL; older builds must not read newer host stores. Restore documented complete backups before downgrading an affected host. No automatic replay on installation and no schedules created by migration. Developer owns deployment and squash merge after review; never restart the running developer instance in verification.
