## Context

The package under `agentic-coding/` has several independent persisted-state readers that historically converted earlier formats on startup. The workflow runtime owns `herdr.db` and currently declares `STORE_SCHEMA_VERSION = 6`; the environment runtime owns `$DEVENV_HOME/db/state.db` with schema version 9; configuration is now canonical JSON (`config.json`, project `.pi/herdr-workflow.json`, and local `tui.json`); telemetry is stored in SQLite and sourced from workflow telemetry files. The unversioned `/api/*` routes and SSE contracts are the current first-party product surface (served by this process and consumed by the TUI client) rather than an obsolete format, so they stay as they are. These are separate concerns and require explicit current-format boundaries rather than broad lexical deletion.

The developer decided that the unversioned `/api/*` surface stays the current product API: it reads no obsolete persisted format, so renaming it to `/api/v1` would be an API break with no old-format reader removed. That modernization is therefore out of scope for this change and must be its own decision and change. Existing workflow/runtime operations and current-format records remain supported. The migration-verifier role and other-project database migration remit are explicitly out of scope.

## Goals / Non-Goals

**Goals:**

- Support current workflow schema v6 and reject every other pre-existing workflow-store version without modifying it.
- Keep current config JSON, TUI preferences, environment schema v9, telemetry and application operations working.
- Remove automatic import/upgrades and old-file fallbacks; old or unknown formats fail clearly or are ignored without rewriting.
- Keep the migration-verifier role/definition and current workflow orchestration, current repair, current pinning and other-project migration guidance.

**Non-Goals:**

- Changing any current workflow schema, environment schema, current JSON preference/config layout, event history semantics, or current API operation semantics.
- Removing versioned workflow definitions required by current v6 pins, the workflow `repair`/`repin` operations, configuration agent presets, or unrelated code-migration documentation.
- Running an app, server, TUI, or CLI against the developer's real store/config; rewriting any live database; or adding worker tasks for the entire repository test suite.

## Decisions

1. **Freeze workflow storage at v6.** Keep `STORE_SCHEMA_VERSION = 6`, the current DDL (including all tables/columns/indexes), and existing `PRAGMA user_version`. A genuinely empty new database gets the v6 DDL and pragma in one initial creation path. Any existing nonempty store with a version other than 6 is rejected before DDL, transactions, locks that mutate, diagnostic insertion or row changes, with exactly `unsupported workflow store version N; this build only reads version 6`. Remove all shape inference and per-version transforms. This replaces “upgrade on open” with fail-closed version selection; changing v6 DDL or dropping `workflow_migration_diagnostics` was considered and rejected because the developer's v6 store has that current shape.

2. **Separate current-format workflow repair from migration.** Remove `operator.migrate`, its preview/effect/telemetry/schema, legacy row import and migration-required views. Retain `operator.repair`, `operator.repin` and current resume semantics only where they repair current v6 state. Preserve exact definition pin resolution and any registered versioned mapping required by workflows already stored in v6; missing pins remain fail-closed instead of being reinterpreted. Remove only old shape aliases whose absence is proven by the current v6 snapshot contract.

3. **Resolve config and preferences only from canonical current files.** Keep explicit config-dir selection, then `AGENTIC_CODING_CONFIG_DIR`, then `~/.config/agentic-coding`; remove `DEVENV_CONFIG_DIR`, TOML fallbacks, import paths, migration journal and `config migrate`. Load current JSON with its existing validation and overlay semantics. `tui.json` remains the sole preferences authority. Unknown/old formats are rejected or ignored, never copied into or used to rewrite canonical files. `DEVENV_HOME` remains because it selects environment runtime state, not workflow config.

4. **Build new environment state at v9; require v9 for existing files.** Preserve the current schema and domain logic, replacing only historical transforms/backups/adoption with a direct current-schema initializer for an empty database and a no-write version gate for an existing one. Existing v9 state is not rebuilt or re-versioned. A non-v9 existing database is refused/ignored; any operator-created recovery or conversion is outside this product.

5. **Use current telemetry formats without historical ingestion.** Continue reading `telemetry.jsonl` and the current telemetry SQLite tables. Remove old-source selection (`traces.jsonl`), old event payload parser fallbacks and old parser/schema re-ingestion. Do not silently add columns, recalculate old indexes or replace a telemetry DB on read. Preserve current parser functionality and current event/query semantics.

6. **Keep the current route surface.** The unversioned `/api/*` operations and event streams are the current product API, not a compatibility shim for an obsolete data format: they read and write only current-format data, and the TUI client calls them. No route is added, renamed, removed or aliased by this change, so every current operation keeps its authorization, effect/ownership boundaries, event semantics and behavior. An `/api/v1` modernization, if wanted, is a separate change with its own caller inventory and its own deliberate break.

7. **Make OpenSpec changes semantic and reviewable.** For each affected existing capability, use `REMOVED Requirements` with reason and migration guidance for obsolete behavior, and `ADDED`/`MODIFIED` current-format behaviors where the contract changes. Do not delete unrelated requirements simply because they contain terms like “legacy”, “migration”, or “repair”. Generate `embedded.generated.ts` rather than editing it directly.

8. **Verify only with disposable fixtures.** Copy `/tmp/agentic-config-snapshot` into an owned temporary directory before loading. Use `HOME=<tmp>` and `AGENTIC_CODING_CONFIG_DIR=<tmp>`. The code-change worker runs focused format-specific tests and lint/type-check; the workflow's test-verifier owns the complete configured test suite. No running app/CLI/TUI with real developer data.

## Risks / Trade-offs

- [Exact v6 DDL or opening semantics drift] → compare the v6 DDL/table/column/index definition and pragma against a v6 fixture; fresh-create and open a copied v6 DB; test old/future version non-mutation. Do not drop `workflow_migration_diagnostics` even though runtime handling is removed.
- [Current workflows have old pins or current JSON has fields also accepted by old formats] → inspect v6 snapshot and parser contracts per field; keep exact pin resolution and fields used by v6; remove only read paths proven to be old-only. Test representative current workflows and copied real current config.
- [Environment v9 DB requires a former migration step even though its marker says v9] → test a real v9-shaped fixture, all current tables/columns/indexes and current operations. Refuse inconsistent/old shapes instead of recreating or advancing them.
- [Telemetry data disappears after dropping `traces.jsonl`/parser fallbacks] → test current `telemetry.jsonl` ingestion, paging and live update from a copied fixture; confirm old-format files are ignored and unchanged. Do not delete telemetry rows or files during open.
- [Unversioned APIs have first-party or external clients] → the developer has directed that the surface stays as it is, so this change takes no break: nothing is renamed or deleted, and every current caller keeps working.
- [OpenSpec/documentation over-removal] → remove only application persisted-format behaviors; preserve migration-verifier/other-project migration guidance, Effect migration guidance, current adapters and atomic rename semantics; run strict spec validation and targeted terminology searches.

## Migration Plan

1. Inventory source references, schema DDL, test fixtures, docs and OpenSpec requirements; capture current v6/v9 schema assertions before deleting old paths.
2. Implement workflow store/runtime, reducer/effect/CLI/contracts and v6 refusal/open tests as one cohesive unit.
3. Implement canonical JSON config/TUI cleanup and root aliases; copy and load the sanitized config snapshot under temporary roots.
4. Implement v9 environment state refusal/current initializer and telemetry current-only ingestion.
5. Remove legacy-only tests/fixtures/docs/exports, update OpenSpec deltas, regenerate embedded sources and refresh god-module export fixtures/ratchets.
6. Run focused tests for each surface, Biome lint, type-check, OpenSpec strict validation and dead-export checks. The workflow test-verifier runs the full configured test suite. Report removed files/modules and a line-count summary from the final diff.

Rollback is a source-code rollback only: no implementation step may upgrade, rewrite or delete a real database/config file. A rollback must not require a data downgrade because this change has no data-write migration. If a current format fails its fixture gate, stop and correct the implementation before handoff.
