## Context

`agentic-coding/src/workflow/effect-runner.ts` implements the `agent.launch` effect. Its `observe` handler is the reuse path: if the run has no recorded `handle` yet, it looks up a live Herdr agent by name (`herdr agent get <name>`) and, if found, sends it a follow-up prompt (`herdr agent prompt`) instead of letting `execute` launch a brand-new tab/pane. The name comes from `runName(changeId, run)`:

```ts
function runName(changeId, run) {
  const suffix = `-${run.role}-${run.id.slice(0, 8)}`;
  const head = changeId.slice(0, Math.max(1, 32 - suffix.length));
  return `${head}${suffix}`.slice(0, 32);
}
```

`run.id` is a fresh UUID generated by `createRun` every time a step is (re-)entered — including every self-loop edge in `definitions.ts` (`core.plan` blocked/failed, `core.plan-approval` comments/reject → `core.plan`, `core.implementation` blocked/failed, `core.verification` fix/failed → `core.implementation`, `core.developer-review` comments → `core.implementation`, `core.archive` blocked/failed). Because the name embeds `run.id`, every one of these re-entries produces a name Herdr has never seen, so the by-name lookup always misses and `execute` always launches a new tab — even though the previous agent for that role is still running idle in its own tab. This directly contradicts the existing `herdr-workflow-prompting` requirement that follow-up runs target the previously detected agent.

Triage and verification roles are handled separately: they are grouped into one shared `verification` tab and placed by `cli.ts#paneForRun` using live-sibling-pane discovery (via `run.handle`, not by name), and their interaction mode is `silent` (one-shot artifact handoff, not a persisted dialogue). They are not part of this bug and must keep working exactly as they do today.

## Goals / Non-Goals

**Goals:**
- Planner (`core.plan`), worker (`core.implementation`), and archive (`core.archive`) agents keep one stable Herdr agent identity across every run/generation of that role within a single workflow instance, so review-comment and blocked/failed retry cycles reuse the existing tab/pane via `herdr agent prompt`.
- No change to how triage/verification roles are named, placed, or reused.
- No change to the assignment message contract (`workflow-agent-assignment`) or to any effect other than `agent.launch`'s naming.

**Non-Goals:**
- Changing triage/verifier tab-sharing or per-round placement behavior.
- Introducing a new persistence mechanism that tracks prior handles in the database (out of scope; name-based detection already exists and is sufficient once the name is stable).
- Changing behavior for concurrent workflows on the same change ID (already out of scope; one active workflow per change ID is assumed elsewhere in the engine).

## Decisions

**Decision: Make `runName` stable per `(changeId, role)` for single-role persistent steps, keep per-run-unique names for grouped steps.**

`runName` will branch on `run.stepId`: for `core.triage` and `core.verification` it keeps today's `-${role}-${run.id.slice(0,8)}` suffix (unchanged behavior); for every other agent step (`core.plan`, `core.implementation`, `core.archive`) the suffix drops the run-id fragment and becomes `-${role}`, so the computed name is identical for every run of that role in the workflow.

Alternatives considered:
- *Carry the previous run's `handle` forward into the new run row at creation time.* Would also fix reuse, but requires new database bookkeeping (looking up the most recent prior run for the same role, copying `handle_json`) and duplicates logic that the existing by-name `observe` lookup already provides. Rejected as a larger, riskier change for the same outcome.
- *Make all roles (including triage/verifiers) use a stable name.* Would let verifier agents from a prior round be silently reused by a later round through the generic `agent.launch.observe` path, bypassing the intentional shared-tab/sibling-split placement logic in `cli.ts#paneForRun` and changing already-correct, spec-covered behavior. Rejected as out of scope and riskier.

## Risks / Trade-offs

- [Two different workflow instances on the same `changeId` role would collide on the same agent name] → Out of scope: the engine already assumes one active workflow per change ID elsewhere (workspace/tab lookups key off `changeId`); this change does not introduce a new instance of that assumption.
- [Herdr agent naming pattern (`^[a-z][a-z0-9_-]*$`, 32 chars)] → Unaffected: the new suffix (`-${role}`) is shorter than the old one, so the existing truncation logic remains within limits.
- [Existing running agents launched under the old, run-id-suffixed name before this fix ships] → No migration needed: those are live Herdr panes, not persisted names; the very next re-entry after the fix simply computes the new stable name, misses (because the still-running agent was registered under the old name), and falls back to `execute`, producing one extra tab that self-heals for all subsequent cycles of that workflow instance.

## Migration Plan

- Code-only change; no schema or data migration (`activeRunForRole` reads existing `workflow_runs` columns; no new tables or columns).
- Full impacted surface (see Addendum below for why this grew beyond the original `runName`-only scope): `agentic-coding/src/workflow/effect-runner.ts` (`runName`), `agentic-coding/src/workflow/runtime.ts` (`WorkflowEngine.activeRunForRole`), and `agentic-coding/src/workflow/cli.ts` (`resolveHandoffIdentity`, used by the `handoff` command). The last two change the `workflow handoff` trust boundary: identity/capability now resolve from the calling process's own `(workflowId, stepId, role)` env plus a freshly-minted, never-persisted token, instead of trusting the process's own `HERDR_RUN_ID`/`HERDR_RUN_GENERATION`/`HERDR_RUN_TOKEN`.
- No feature flag: behavior only differs for the affected self-loop scenarios and is strictly closer to the already-documented spec.
- Rollback: revert all three files together (`runName`, `activeRunForRole`, `resolveHandoffIdentity`). Reverting only `runName` while leaving `resolveHandoffIdentity` in place would silently keep the revised handoff trust boundary active without the reuse behavior it was built to support — do not partially revert.

## Open Questions

None — the affected roles, ownership boundary (single-role vs. grouped steps), and naming rule are fully determined by existing code and the `herdr-workflow-prompting` spec.

## Addendum: reused-agent identity refresh (raised by quality-verifier QV-001/QV-002)

The stable-naming fix above made the `observe` reuse path find and re-prompt the still-running agent, but the quality-verifier found that agent's own OS process env is fixed at its original `agent start` and is never refreshed for the new generation; `workflow handoff` resolves `HERDR_RUN_ID`/`HERDR_RUN_GENERATION`/`HERDR_RUN_TOKEN` exclusively from `process.env`, so the reused agent's eventual handoff used the prior, already-completed run's stale identity and was rejected (`stale-run`/`unauthorized`). This directly contradicts the "No new persistence mechanism" non-goal above, which assumed name stability alone was sufficient — it is not, because process env cannot be updated for an already-running process without restarting it (which would defeat the fix).

A first attempt at resolving this (a `HERDR_RUN_MARKER` file rewritten on every reuse with `{runId, generation, token, outputPath}`) was itself rejected by the security-verifier: every role in the workflow shares the same worktree with "read and edit repository" permission, so any sibling role's process could read another role's plaintext bearer capability token off disk and impersonate it in `agentic-coding workflow handoff` (SV-001/SV-002), and the marker write path had no symlink guard (SV-003).

Resolution (superseding the marker-file attempt): resolve the current run to hand off from the calling process's own **stable, non-secret** identity — `HERDR_WORKFLOW_ID`/`HERDR_STEP_ID`/`HERDR_ROLE` — instead of its run-scoped `HERDR_RUN_ID`/`HERDR_RUN_GENERATION`/`HERDR_RUN_TOKEN`. Unlike the run-scoped fields, `HERDR_WORKFLOW_ID`/`HERDR_STEP_ID`/`HERDR_ROLE` never change across a persistent role's generations (they identify *what this process is*, not *which run it was last given*), and by construction at most one run per `(workflowId, stepId, role)` is ever `working` at a time. `WorkflowEngine.activeRunForRole(repo, workflowId, stepId, role)` looks that run up directly from the local, trusted engine store, and the capability token is minted fresh, in-process, immediately before the handoff dispatch via the existing `issueRunCapability` — it is never written to disk, logged, or exposed through any env var, so no sibling role's process can read or replay it. This is strictly no less secure than the pre-existing (pre-marker-file) design, which already trusted a process's own env for its own identity; it does not introduce any new cross-role-readable secret. No pinned instruction asset text changes; this is CLI/engine-internal plumbing the agent is not required to know about.

### Addendum follow-up: repair-race window (quality-verifier QV-001, second review)

`activeRunForRole` initially matched any run with status `pending` **or** `working`. The quality-verifier found this reopened a different hole: `operator.repair` can expire a stale run and synchronously create a fresh `pending` run for the same `(workflowId, stepId, role)` in one transaction, while the still-alive stale process (never yet re-prompted) is only asked to stop asynchronously via a queued, undrained `agent.stop` effect. In that window, the stale process's own `workflow handoff` call would previously have been rejected outright (its frozen `HERDR_RUN_ID` pointed at a now-expired run, caught by `agentHandoff`'s `stale-run` check); with role-based resolution it would instead silently resolve to — and be able to mark blocked/failed — the unrelated fresh run it was never told about, since `activeRunForRole` only keyed on the role tuple, not on which specific run/generation the caller actually knew about.

Fix: `activeRunForRole` now requires status **`working`**, not `pending`. A run only reaches `working` when its `agent.launch` effect actually completes (the engine atomically sets `handle_json` and `status='working'` together), which for a persistent role only happens once the reuse `observe` path has confirmed the pane is live and has actually delivered the new prompt to it. Excluding `pending` closes the repair-race window (a not-yet-launched run can never be handed off) while fully preserving the legitimate reuse case (which always completes `agent.launch` — and reaches `working` — before any handoff for that generation is possible).
