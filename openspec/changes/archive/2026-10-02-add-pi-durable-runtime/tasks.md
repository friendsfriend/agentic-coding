## 6. Dashboard agent session view

- [x] 6.1 Add a live agent session view attaching via the host client `watch` and rendering status, a bounded host-unavailable state — implemented as `src/tui/dash/ui/AgentSessionModal.tsx`, rendered through the existing `Overlays`/`GenericModal` dashboard-modal system (`modal.active === "agent-session"`) rather than a standalone `routes/AgentSessionRoute.tsx` file; App.tsx owns a real `HostClient.watch()` subscription (`src/tui/dash/App.tsx`'s `openAgentSession`) that live-updates the modal's status lines via `renderAgentSessionSummary` on every frame, torn down on close/unmount. Streaming-answer text, running-tool-output detail, and model/usage are not separately broken out — `renderAgentSessionSummary`'s bounded status/running-tool/queue/entry-count text is the whole live view, not just an opening snapshot (the generation-3 version only fetched one frame; this one keeps the subscription open for the modal's lifetime). A connection failure surfaces as status text in the same area ("Could not reach the agent host: …"), not a distinct state. Verified with `test/dash/agentSessionModal.test.tsx` (component-level `testRender`) and the full `test/dash/*.test.tsx` suite (136 tests) re-run clean after the change.
- [x] 6.2 Add the input line (submit) and abort; "close" is also implemented. Follow-up vs. steer is not a separate key: every submission is delivered with `whenBusy: "followUp"` (matches `AgentAdapter.prompt()`'s own default), so there is no dedicated "steer" action. Abort and close are typed slash commands (`/abort`, `/close`) submitted through the same always-focused `<input>`, not separate key bindings — discovered empirically while building this view that a focused OpenTUI `<input>`/`<textarea>` never forwards Escape to `onKeyDown` (it does forward ordinary characters and Tab), so an "Esc closes" binding the way `NewWorkflowModal` appears to rely on would silently do nothing; this is noted in `AgentSessionModal.tsx`'s module comment for whoever next touches that pattern. All four behaviors (send, abort-not-send, close-not-send/abort, empty-submission-is-a-no-op) are each pinned by a `testRender`-driven test.
- [x] 6.3 Route Enter on a `pi-durable` Agents-panel row to the session view; keep pane focus for other runtimes — implemented in `src/tui/dash/handlers/keys.ts`; the `WorkflowView`/`DashboardData` projection carrying `hostSocket`/`conversationId`/`runId` to the panel is focused-tested end to end.
- [x] 6.4 Declare the session keybinds (footer + `?` help) — done via `GenericModal`'s own `help` prop (which self-registers into the shared `?`-help overlay via `registerModalHelp`), the same mechanism every other feature-specific dashboard modal already uses (`CostModal`, `FindingsModal`, `PresetSwitcherModal`) — **not** a new `agent-session` context in the shared `src/tui/dash/keybinds.ts` catalog as originally specified, since that catalog is used only for panel-level/global keys in this codebase, never per-modal ones (confirmed by grep: none of the existing feature modals appear there either).
