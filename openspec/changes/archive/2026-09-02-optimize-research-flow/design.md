## Context

See proposal.md - Why. The `research` workflow graph, its steps, and its allowed outcomes are defined in `agentic-coding/src/workflow/definitions.ts` inside the `manifests(...)` factory (the `wikiGate`-conditional `research` manifest). Today its edges are `core.research` → `core.wiki` → `core.wiki-approval` → `core.closed`, with the `core.wiki-approval` approve edge carrying the `wiki.verify` effect and going straight to `core.closed`. `core.completed` and `core.closed` step definitions already exist and are reused by the other flows.

Two runtime/UI surfaces implement the developer experience:
- `agentic-coding/src/workflow/runtime.ts` `actions(...)` computes the developer-available actions per step. For the research flow it currently offers `close-research` at every active step and, at `core.wiki-approval`, `approve-wiki` / `review-comments`. The `close-research` handler transitions directly to `core.closed` whenever `definition.id === "research"` and the step is not already closed.
- `agentic-coding/src/tui/dash/App.tsx` and `agentic-coding/src/tui/dash/data.ts` decide which UI opens. `openPlanReview()` already handles wiki review (`reviewKind === "wiki"`, `loadWikiSnapshotChanges/Diff`, `saveWikiReview`) and is opened directly for the plan/wiki review gates — but guarded by `data().state.definition?.id !== "research"`, so the research flow falls through to the generic `ListViewModal` built from `requiredUserActionFor(...)` in `data.ts` (the "Approve wiki / Request wiki changes / Close research" list).

The wiki agent's assignment for a research-originated `core.wiki` run is built in `effect-runner.ts` `assignmentFor(...)`, and the wiki role's behavior text lives in `agent-definitions/instructions/wiki.md`. Originally `wiki.md` was shared verbatim by both the research `core.wiki` step and the openspec `core.wiki` step, gated internally by a "Research handoff input" section that only applied when a handoff was present, and `assignmentFor(...)`'s `isResearchWikiStep` branch keyed off `snapshot.definition.id === "research" && run.stepId === "core.wiki"`. Developer review on this change rejected that conditional-prompt shape (a single `wiki` role reading a step/workflow-conditional instruction file) as the wrong abstraction: research-handoff drafting and openspec/implementation drafting are different tasks and should be different agents. The registry already has precedent for a step pinning several instruction assets and picking one per role at render time (`agentic-coding/src/workflow/assignment.ts` `renderAssignment` selects `verification-${role}.md` for the `core.verification` step's per-severity verifier roles); this change reuses that pattern for `core.wiki` instead of introducing a new step id.

## Goals / Non-Goals

**Goals:**
- Give the research-handoff wiki step its own dedicated agent role and instructions, directive-first, so it stops broad rediscovery, without changing the openspec/implementation `wiki` role's behavior.
- Reuse the existing standard wiki review popup for the research flow at `core.wiki-approval`.
- Route research approval through `core.completed` and gate closing there; remove `close-research` after handoff.

**Non-Goals:**
- No change to the handoff contract/schema (`researchHandoffContract`), the CLI's `research-handoff`/`start`/`status`/`action` argument surface, or the researcher (`core.research`) role or instructions.
- No change to the openspec/wiki-only/wiki-comments wiki review or graph, and no change to the `wiki` role's write authorization, promotion rights, or source-repository boundary.
- No new review UI component — reuse `openPlanReview()`/`saveWikiReview` as-is.
- No new workflow step id — `research-wiki` is a second role on the existing `core.wiki` step, not a new step.

## Decisions

**D1: Add `core.completed` to the research graph and re-point the approve edge.**
Change the `research` manifest `steps` to `["core.research", "core.wiki", "core.wiki-approval", "core.completed", "core.closed"]` and its edges so `core.wiki-approval` approve (keeping the `wiki.verify` effect) targets `core.completed`, plus a `core.completed` close edge to `core.closed`. This reuses the same `core.completed` close gate the standard flows use, giving "close only after approval" for free via the existing completed-step action. The `core.wiki-approval` comments edge back to `core.wiki` is unchanged. Because the research manifest is versioned by the same `definitionVersionForPolicy`/version machinery as the other manifests, this is a new definition version; existing pinned research instances keep their old pin. Alternative considered: keep `core.wiki-approval` → `core.closed` and instead block `close` in runtime until approval — rejected because it diverges from the standard flow's completed-gate pattern and duplicates gating logic.

**D2: Gate `close-research` availability by step, not just definition.**
In `runtime.ts` `actions(...)`, only offer `close-research` when `currentStep === "core.research"` (the purely-conversational stage), and stop offering it at `core.wiki`/`core.wiki-approval`. At `core.completed` the existing completed-actions branch already yields `close` (research is not in the proposal-only/wiki exclusion list, so it would also offer `create-pr` — research must be added to the list that suppresses `create-pr`, leaving only `close`). Keep the `close-research` handler itself, but tighten its guard so it rejects when the step is not `core.research` (defense in depth against a stale revision dispatch). Alternative considered: remove `close-research` entirely and rely only on `core.completed` — rejected because a purely conversational Q&A session with nothing to document must still be closable (developer decision, option 1).

**D3: Reuse the standard wiki review popup for research.**
Remove the `data().state.definition?.id !== "research"` guards in `App.tsx` (in `openRequiredUserAction` and the auto-open effect) so the `wiki-review` user action opens `openPlanReview()` directly for the research flow, exactly as for the other flows. `openPlanReview()` already selects `reviewKind === "wiki"` from the step id (`core.wiki-approval`) and loads the wiki snapshot, so no popup-content changes are needed. Update `data.ts` `requiredUserActionFor(...)` so the research `wiki-approval` branch no longer emits the `close-research` list item (the popup, not a list, drives approve/request-changes), and so the research `core.wiki` phase no longer advertises `close-research`. Alternative considered: build a research-specific review list — rejected; the whole point is UI parity with the standard flows.

**D4: Directive-first wiki drafting for the research-handoff wiki agent.**
Instruct the research-handoff wiki agent to (a) begin by creating/updating exactly the directive-named concepts with the listed claims and (b) restrict repository/wiki inspection to targeted corroboration of those directives instead of broad rediscovery. This is now the entire content of a dedicated instructions file (`wiki-research.md`, see D5) rather than a conditional section of the shared file, and the `effect-runner.ts` assignment text is keyed off the agent's role rather than a workflow/step check. Because the openspec `core.wiki` assignment always runs the separate `wiki` role and reads `wiki-openspec.md`, never `wiki-research.md`, the openspec path is structurally unaffected (no conditional to get wrong). Superseded alternative (originally chosen, then reversed by developer review): keep one shared `wiki` role/file with an internal "Research handoff input" section conditioned on a research handoff being present — rejected because it does not read as, and does not behave as, two different agents for two different tasks, and because instruction-asset digests are pinned per step, so a single shared file with a conditional section externally looks identical for both call paths, inviting exactly this review pushback.

**D5: Two dedicated wiki roles, one shared step id, per-role instruction assets.**
Add a second agent role, `research-wiki`, used only by the research manifest's `core.wiki` step in place of `wiki`. Both roles keep running on the existing `core.wiki` step id — no new step, no graph change, no change to the step-id-keyed checks already in `runtime.ts` (`validateSourceBaseline`, `researchWikiPromotion`, wiki-approval review UI) or `cli.ts` (`authorizeWikiWriter`'s `stepId === "core.wiki"` gate, now additionally accepting either wiki-writing role). Split `wiki.md` into three files: `wiki.md` keeps the shared contract every wiki-writing role needs verbatim (source-repository boundary, project/shared concept-naming scoping, update-existing-before-creating sequence, OKF authoring rules, review-comment revision handling); `wiki-openspec.md` holds the `wiki` role's discovery-based "how do I decide what to document" guidance (previously "Research before writing"); `wiki-research.md` holds the `research-wiki` role's directive-first guidance (D4), written unconditionally since every run of this role follows a handoff. `agentic-coding/src/workflow/definitions.ts` pins all three files (plus the protocol) under `INSTRUCTION_BY_STEP["core.wiki"]`; `agentic-coding/src/workflow/assignment.ts` `renderAssignment` is generalized so a `wiki-` prefixed asset is treated the same way a `verification-` prefixed asset already is — included only for the one role it names (via a `{ wiki: "wiki-openspec.md", "research-wiki": "wiki-research.md" }` map) — while `wiki.md` itself (no prefix) is always included, exactly like `verification.md`. `runtime.ts` `roleForStep` returns `research-wiki` instead of `wiki` when `snapshot.definition.id === "research"`. `cli.ts` `rolesForDefinition` makes the same substitution when building the research workflow's default routing, and its wiki-write authorization (`authorizeWikiWriter`, the `wiki write` role gate) and `wiki.ts`'s forced-draft-status check accept both roles identically — the split changes drafting approach and instructions only, never write authorization, promotion rights, or the source-repository boundary. Alternative considered: a dedicated `core.research-wiki` step id instead of a second role on `core.wiki` — rejected as unnecessarily large; it would touch the graph shape and every step-id-keyed check for no behavioral benefit over the per-role-asset approach, which already has a working precedent in this codebase for `core.verification`.

## Risks / Trade-offs

- [New research definition version could strand in-flight research instances mid-graph] → Existing instances keep their pinned older definition and complete on the old graph; only newly started research uses the new version. This mirrors how every prior graph change to these manifests is versioned.
- [Removing `close-research` after handoff could trap a developer who no longer wants the drafted wiki] → The `core.wiki-approval` request-changes path and, ultimately, approval + explicit `close` at `core.completed` still terminate the flow; the developer is never blocked, only required to resolve the draft first (the intended behavior).
- [Splitting one role into two could silently change openspec wiki behavior if the shared base file drifts from the per-role files, or if a wiki-write authorization check misses the new role] → The shared `wiki.md` base is a pure subset of the original file's always-applicable content (verified by the pre-existing `workflow-wiki-scope.test.ts` cross-file consistency test, kept passing); the `research-wiki` role only ever reads `wiki-research.md` and never `wiki-openspec.md` (enforced structurally by `assignment.ts`'s per-role asset map, not by a conditional an author could get wrong); every `role === "wiki"` authorization/enforcement site (`cli.ts` wiki-write gate, `wiki.ts` forced-draft-status check) was audited and updated to accept `research-wiki` identically, and both are exercised by tests.
- [A new role widens two authorization surfaces — wiki-write and forced-draft-status — that are security-relevant] → Both `research-wiki` and `wiki` are granted identical, narrower-than-developer rights (write unverified drafts only, never `stable`/`verified`, never archive/verify); the change only adds `research-wiki` to the same allow-list `wiki` was already on, and the existing `wiki write is not permitted for role` rejection test coverage is extended to assert this for `research-wiki` too.
- [Removing the App.tsx research guards affects both the manual-open and auto-open code paths] → Both call sites (`openRequiredUserAction` and the auto-open `createEffect`) must be updated together, and the demo/test profile paths verified, so the popup opens consistently.

## Migration Plan

Pure in-repo behavior change; no data migration. The new research definition version registers alongside the old ones (the registry keeps all versions), so rollback is reverting the source change — pinned instances are unaffected either way. Update the pinned instruction digests for `wiki.md`, and register the two new pinned assets `wiki-openspec.md` and `wiki-research.md`, in the same change (`bun run build` regenerates the embedded digest bundle) so the assignment renderer accepts the edited/added assets.
