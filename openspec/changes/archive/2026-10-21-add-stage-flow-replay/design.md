## Context

`add-stage-flow-blocks` introduces a typed block layer and a linear plan runner.
A reviewed plan can now execute in one `stage_run` call, but the call is still
started by a model and the plan is still re-read on every run. The same stable
scenario should be executable as a normal Playwright test with no model in the
execution loop and with parameters supplied by the approved plan rather than
baked into generated code.

The existing `browser_run_script({ save: true })` path already emits a rerunnable
`@playwright/test` spec, but it is a reproduction of one ad-hoc script. It has no
block contract, no plan identity, no catalog and no workflow integration. This
change defines the missing replay contract and keeps the ad-hoc script in its
current role.

The stage workflow currently produces `core.stage-test-plan@1`, approves it when
the stage policy requires it, runs the `stage-tester`, and validates a
`core.stage-report@1`. Replay must fit that lifecycle rather than create a second
workflow. The plan contract is extended in place: `flowId`, `inputs` and
per-route `expectationIds` are optional additions, so existing `@1` plans remain
valid and no `@2` is introduced.

## Goals / Non-Goals

**Goals:**

- Compile a validated block plan into a readable, reviewed Playwright spec and a
  sidecar flow manifest.
- Make one compiled flow reusable with different input values. Input values live
  in the approved plan revision; the generated spec reads them at runtime and is
  not regenerated when only values change.
- Execute a saved flow with no model turn per step and no model in the green
  execution path.
- Make replay eligibility explicit and safe: right stage, approved route, valid
  input schema, approved input values and the exact block versions/digests.
- Ingest replay journal events and evidence through the existing stores.
- Produce the existing report contract deterministically when the flow covers
  every expectation, and route failures to a bounded heal packet.
- Let a replay use the stage API for setup, assertions and cleanup under the
  same policy as `stage_api_request`.
- Support parallel independent flows in a suite without weakening isolation, and
  allow the same flow to run more than once with different inputs.
- Keep the generated spec runnable in CI with typed inputs, traces, videos and
  structured results.

**Non-Goals:**

- An LLM inside a spec or a green replay.
- Automatic code edits, auto-commit, auto-merge or auto-promotion after a
  failure.
- Replacing plan approval or report validation.
- Using an input override to bypass the approved plan revision.
- Arbitrary generated code at runtime. Only checked-in, reviewed specs are
  replay-eligible.
- A browser-engine or CDP change.
- Parallelising flows that share data, sessions or ordering.

## Decisions

### D1. The spec is generated from the same blocks and reads typed inputs at runtime

`stage_run({ plan, save: true })` runs the normal validation, then emits:

```text
stage-flows/
  customer-address/
    flow.spec.ts
    flow.json
```

A replay plan uses the existing `core.stage-test-plan@1` with the optional
`flowId`, `inputs` and route `expectationIds` fields. Route arguments bind plan
inputs with `{{ inputs.<name> }}`; the plan runner resolves those references, and
the generator maps them to `stage.input` calls. The plan's `inputs` object is the
approved value set for one run.

`stage_run` may still accept a standalone `StageBlockPlan` for a one-off
execution. Saving a flow requires the approved stage plan: `flowId`, `inputs`,
`expectationIds`, and a block on every route step. The generator projects the
route to the same linear block plan the runner uses, preserving route step ids.

`flow.spec.ts` is readable Playwright code, not a serialized plan and not a copy
of the input values:

```ts
// Generated by stage_run. Do not edit by hand; regenerate from the approved plan.
import { test } from "../../src/stage-blocks/fixture.ts";
import {
  fillCustomerAddress,
  openCustomer,
} from "../../src/stage-blocks/crm/index.ts";

test.describe("customer-address", () => {
  test("fills and saves a customer address", async ({ stage }) => {
    const customer = await stage.run("open-customer", openCustomer, {
      customerId: stage.input("customerId"),
    });
    await stage.run("fill-address", fillCustomerAddress, {
      customerId: customer.customerId,
      street: stage.input("street"),
      city: stage.input("city"),
      postalCode: stage.input("postalCode"),
      country: stage.input("country"),
    });
  });
});
```

The fixture's `stage.input(name)` reads the run input envelope, validates the
value against the manifest's `inputSchema`, and returns the typed value. The same
spec can therefore run again with a new approved plan revision whose route is
unchanged and whose `inputs` differ; only the plan approval changes, not the
generated code.

The generator:

- refuses a plan with a step that has no block (a mixed plan is not a replay
  flow);
- requires `flowId` for a saved flow;
- maps `{{ steps.<id>.outputs.<path> }}` to local variables and property access;
- maps `{{ inputs.<name> }}` to `stage.input("<name>")`;
- derives `inputSchema` from the input placeholders and the receiving block
  parameter schemas; a name used at incompatible types fails generation;
- emits route step ids so the fixture can map results to expectations;
- refuses a literal that matches a configured stage secret;
- formats the result with the repository formatter and checks that it
  type-checks;
- writes a header that says the file is generated and must not be hand-edited;
- writes the files to the working tree only; it SHALL NOT commit, push or open a
  pull request. A reviewed code workflow owns check-in and review.

The spec imports the block functions from the repository, so a block change is a
normal code review. The fixture supplies the same `StageContext` as the plan
runner. A block cannot tell whether it is running under `stage_run` or under
`stage_replay`.

**Alternative rejected:** bake the approved values into the spec. It would make
every data change a code regeneration and review, and it would prevent one flow
from serving multiple data sets.

**Alternative rejected:** A generic spec that reads the plan JSON and calls a
runner. It would avoid code generation, but it would hide the flow from review,
make test output unreadable and turn every change into a runtime data edit. The
readable spec is the review surface; only the inputs are data.

### D2. A flow manifest makes route and input eligibility explicit

`flow.json` is the sidecar contract:

```json
{
  "flowId": "customer-address",
  "title": "Customer address",
  "generatedFrom": { "planId": "plan-2026-10-21-001", "revision": 3 },
  "stage": "grid-int",
  "applications": ["crm"],
  "roles": ["clerk"],
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["customerId", "street", "city", "postalCode", "country"],
    "properties": {
      "customerId": { "type": "string" },
      "street": { "type": "string" },
      "city": { "type": "string" },
      "postalCode": { "type": "string" },
      "country": { "type": "string" }
    }
  },
  "inputExamples": [
    {
      "customerId": "C-1001",
      "street": "Teststr. 1",
      "city": "Berlin",
      "postalCode": "10115",
      "country": "DE"
    }
  ],
  "routeHash": "sha256:...",
  "specHash": "sha256:...",
  "blockVersions": {
    "crm.customer.open": "1.4.0",
    "crm.customer.fillAddress": "1.2.0"
  },
  "blockDigests": {
    "crm.customer.open": "sha256:...",
    "crm.customer.fillAddress": "sha256:..."
  },
  "routeSteps": [
    {
      "routeStepId": "open-customer",
      "block": "crm.customer.open",
      "inputs": ["customerId"],
      "expectationIds": ["E1"]
    },
    {
      "routeStepId": "fill-address",
      "block": "crm.customer.fillAddress",
      "inputs": ["street", "city", "postalCode", "country"],
      "expectationIds": ["E1", "E2"]
    }
  ]
}
```

`routeHash` covers the flow id, route step ids and order, application/role scope,
block ids, canonical argument structure (input placeholders and literal
constants), output wiring, expectation mapping and captures. It deliberately
excludes input values, the source plan revision, generated prose and timing, so a
new plan revision that changes only `inputs` keeps the same route identity.

`inputSchema` is derived at generation time; `inputExamples` are review aids and
are not used for eligibility. `specHash` detects a hand edit to the generated
spec. `blockDigests` catch a source change that did not bump a version.

A flow is replay-eligible only when all of the following hold:

1. the pinned stage equals the manifest stage, or the manifest explicitly lists
   the pinned stage in `stages`;
2. the approved plan names the manifest `flowId`;
3. the approved plan's route hash matches the manifest `routeHash`;
4. the approved plan's `inputs` validate against `inputSchema`, contain every
   required property and no undeclared property;
5. the registry's block versions and digests match `blockVersions` and
   `blockDigests`;
6. the checked-in spec's hash matches `specHash`;
7. every route step maps to a manifest route step with a block, and every
   expectation in the plan is covered;
8. the stage applications and roles include the manifest's applications and
   roles.

The source plan revision and `inputsHash` are recorded in the result, not used as
the route identity. `inputsHash` is the canonical JSON hash of the approved input
object, so key order does not change it. A new plan revision with the same route
and a different valid input set is eligible without regenerating the spec; a
changed route, stage, block or expectation mapping is not.

If any condition fails, `stage_replay` SHALL refuse with a specific reason and
the workflow SHALL fall back to `stage_run` or require a recompile/re-approval.
It SHALL NOT silently execute a drifted flow or substitute an unapproved value.

**Alternative rejected:** include input values in route identity. That ties a
flow to one data set and forces regeneration for every new customer or order,
which defeats reuse.

**Alternative rejected:** trust the flow id alone. That lets a changed block, a
hand-edited spec, a different stage or an unapproved input set run without
review.

### D3. Replay is a separate process with the existing stores

`stage_replay({ flowId, stage, session?, inputs?, dryRun? })` starts a Playwright
process:

```text
bunx playwright test stage-flows/customer-address/flow.spec.ts \
  --project=stage-flows \
  --reporter=src/stage-blocks/reporter.ts
```

The process receives:

- the stage id and declared applications/roles;
- the approved plan id/revision and its `inputsHash`;
- a bounded run-input file containing the approved input values, validated before
  the process starts and removed after it exits;
- a short-lived run token, not raw credentials;
- the workflow evidence directory and run id;
- the trace/video policy.

When `inputs` is omitted, `stage_replay` uses the approved plan's inputs. When an
explicit `inputs` object is supplied in a workflow run, it SHALL match the
approved plan's `inputsHash`; otherwise the tool refuses with
`flow-inputs-unapproved`. New values are a new plan revision and a new approval.
A dry run may validate a proposed input set against the manifest schema without
starting a browser, but it SHALL clearly report that the values are not approved.

The fixture:

- builds a `StageContext` over a browser context opened by the runner, not a
  second browser pool;
- validates the run inputs against `inputSchema` before the first block;
- records `test.step` spans and writes ordered replay events to
  `stage-replay-events.jsonl`;
- writes screenshots, scoped snapshots, traces and videos to the run evidence
  directory and a manifest fragment;
- writes `stage-run.json` at test end, including per-step status, duration,
  outputs, `inputsHash`, event offsets and evidence ids;
- never writes into `stage-journal.jsonl` directly.

The engine ingests the event file: it validates evidence ids, applies the shared
redactor, allocates journal sequence numbers, appends to `stage-journal.jsonl`,
merges the evidence manifest and then marks the replay run complete. This keeps
one journal and one manifest even though the execution happened in another
process.

**Alternative rejected:** letting the Playwright process append the journal
directly. Two writers would race on sequence numbers and would duplicate the
redaction and evidence rules.

### D4. The success path produces the same report contract

To make a deterministic report possible, the existing `core.stage-test-plan@1`
gains optional `flowId`, `inputs` and per-route `expectationIds`. These are
additive fields; a plan without them remains valid for exploratory execution.
The planner populates `expectationIds`; the plan review shows the flow id, the
approved input values, the input schema and the coverage.

A replay run maps results to `core.stage-report@1` as follows:

- an expectation covered only by passing steps is `pass`;
- an expectation covered by a failed step is `fail`, with severity mapped from
  the plan priority (`critical`→`critical`, `high`→`major`, `medium`→`minor`,
  `low`→`info`) unless the flow manifest declares a more specific severity;
- an expectation whose covering step was skipped because an earlier dependency
  failed is `blocked`, with the dependency named;
- an expectation not covered by the flow is `inconclusive` with a reason, unless
  the plan already declares it as not tested;
- `applicationVersions` comes from the stage catalog or the flow's availability
  check;
- `createdData` maps from the plan's declared data creation, with cleanup hints
  from the flow manifest where present;
- knowledge observations are empty unless a block emitted a knowledge event
  through the replay journal; the report validator still requires every cited
  journal entry to exist.

The engine runs the existing report validation and render effect. A replay report
is not a new report type; it is the same `core.stage-report@1` with deterministic
values. If the flow cannot cover every expectation, the workflow routes to the
normal `stage.execute` tester instead of fabricating a verdict.

**Alternative rejected:** let the replay runner write the Markdown report
directly. It would bypass the existing validation, redaction and evidence rules.

### D5. A failure produces a heal packet, never an automatic edit

On a failed replay, the engine writes a bounded `stage-heal.json` packet:

```json
{
  "flowId": "customer-address",
  "planRevision": 3,
  "inputsHash": "sha256:...",
  "failingStep": "fill-address",
  "block": "crm.customer.fillAddress",
  "version": "1.2.0",
  "subStep": "save address",
  "expected": "Address saved",
  "observed": "Validation error: postal code",
  "retryable": false,
  "evidenceIds": ["..."],
  "trace": "evidence/.../trace.zip",
  "scope": "form[data-testid=address]",
  "lastPassingStep": "open-customer"
}
```

The packet is attached to the workflow and returned to the tester. The tester may
use the scoped snapshot, trace and console/network tail to diagnose the failure
and report it. A stage workflow SHALL NOT edit a block, edit a generated spec,
commit, push or recompile on its own. A separate reviewed code workflow may use
the packet to heal the block, run the block contract test, regenerate the spec and
ask for re-approval. The stage run records the failure and remains auditable.

**Alternative rejected:** auto-heal in the stage workflow. It would let a test run
change the code it is testing and would bypass review.

### D6. API-first setup and assertions use the same stage policy

The replay `StageContext` adds `ctx.api` beside the page surface:

```ts
const customer = await ctx.api.request({
  app: "crm",
  role: "clerk",
  method: "POST",
  path: "/v1/customers",
  body: { name: "Stage test" },
});
```

`ctx.api` reuses the existing `stage_api_request` policy:

- the application must be declared by the pinned stage and be an API application;
- the role must be declared;
- a path is relative to the application origin; absolute URLs are refused;
- a read-only stage refuses a state-changing method;
- request and response sizes are bounded;
- authorization, cookie and configured secrets are redacted;
- a state-changing API call is a `write` effect for plan validation and approval.

A block that uses `ctx.api` for setup or cleanup declares the effect accordingly.
An assertion that only reads through the API is a `read`. The generated spec does
not contain a token; the fixture receives a short-lived run token from the
server. Plan inputs are test data, not credentials; a credential is resolved
through `ctx.secret`.

**Alternative rejected:** a separate API client in the spec with credentials from
the environment. It would duplicate policy and make secrets part of the spec.

### D7. Parallel replay is a suite of independent flow entries

A suite manifest lists flow entries and declares independence. Each entry binds
a flow id to its own input object, so the same flow can run more than once with
different data:

```json
{
  "suiteId": "crm-regression",
  "parallel": true,
  "stopOnFailure": false,
  "flows": [
    {
      "flowId": "customer-address",
      "inputs": {
        "customerId": "C-1001",
        "street": "Teststr. 1",
        "city": "Berlin",
        "postalCode": "10115",
        "country": "DE"
      }
    },
    {
      "flowId": "customer-address",
      "inputs": {
        "customerId": "C-1002",
        "street": "Teststr. 2",
        "city": "Munich",
        "postalCode": "80331",
        "country": "DE"
      }
    },
    {
      "flowId": "customer-search",
      "inputs": { "query": "acme" }
    }
  ]
}
```

`stage_replay({ suiteId })` validates each entry's inputs against its flow
manifest, then runs the entries in separate browser contexts with distinct run ids
and journal segments. Worker count is bounded by the suite setting,
`browser.max_sessions` and the CI worker setting. A suite SHALL refuse
`parallel: true` if any entry declares shared data, a fixed sequence or a
dependency on another entry. The same flow id may appear more than once only when
the entries do not share created data. A failed entry does not cancel another
entry unless the suite declares `stopOnFailure: true`.

A suite run is a regression/CI path, not a shortcut to a workflow report. In a
stage workflow, every entry SHALL match an approved plan revision's `flowId`,
route hash and `inputsHash`; an entry without that approval is refused. A
standalone CI suite may use a reviewed input file but does not claim a
`core.stage-report@1`.

**Alternative rejected:** parallelising every flow by default. Stage data is often
shared; the suite must opt in and declare independence.

### D8. CI uses the same specs, fixture and result contract

A generated flow is a normal Playwright test. CI runs:

```text
STAGE_FLOW_INPUTS=.ci/customer-address-inputs.json \
bunx playwright test stage-flows/customer-address/flow.spec.ts \
  --project=stage-flows \
  --reporter=src/stage-blocks/reporter.ts
```

The CI configuration:

- supplies stage credentials through the existing secret environment, never in
  the spec or manifest;
- supplies flow inputs from a JSON file that is validated against the flow's
  `inputSchema` before the test starts; a missing, extra or mistyped value fails
  the job;
- reads no input value from an unvalidated environment variable;
- sets `trace: "retain-on-failure"` and `video: "retain-on-failure"`;
- writes `stage-run.json`, the JUnit/HTML report and the evidence directory as
  artifacts;
- uses the same report mapping only when a `stage-test` workflow supplies an
  approved plan revision and `inputsHash`; a standalone CI run produces the
  result contract, not a workflow report;
- fails the job on a non-zero Playwright exit, an input-schema violation or an
  invalid result contract.

A CI run without the server can use a token/endpoint pair; the fixture keeps the
same policy checks and never bypasses the stage allow-list.

**Alternative rejected:** a second CI-only runner. It would drift from the local
replay and the block contract tests.

## Risks / Trade-offs

- **Generated code drifts from the plan.** Mitigation: `routeHash`, `specHash` and
  `blockDigests` make route/code drift explicit; input-only changes are a plan
  revision and do not require a spec diff.
- **A generated spec is hard to read.** Mitigation: one call per route step, no
  serialized JSON, no generated helper logic; route step ids and expectation
  mappings are comments/metadata.
- **Reusing a flow with new values hides a data change.** Mitigation: input values
  are never in the spec; every run records `inputsHash`; the plan review shows the
  values and the flow manifest schema; a changed value set is a new approved plan
  revision.
- **Inputs are mistaken for secrets.** Mitigation: plan inputs are test data only;
  credentials use `ctx.secret`; the run-input file is bounded and removed; result
  and journal carry only `inputsHash` unless a block explicitly captured a value.
- **The Playwright process and the server disagree about evidence.** Mitigation:
  one event/manifest ingestion path with validation and sequence allocation in
  the server; the process never writes the journal directly.
- **A parallel suite races on data.** Mitigation: explicit `parallel: true`, a
  declared independence check, per-entry inputs and shared-data declarations;
  default is sequential.
- **A replay gets treated as a substitute for a missing expectation.** Mitigation:
  the report map marks uncovered expectations `inconclusive` and the existing
  validator still requires every expectation.
- **A block changes without a version bump.** Mitigation: block digests in the
  manifest and registry; a digest mismatch makes the flow ineligible.
- **CI secrets leak through traces or reports.** Mitigation: the existing
  redactor, no credentials in specs or inputs, bounded traces, and evidence
  manifest validation before storage.

## Migration Plan

1. Ship the spec generator, fixture, manifest and replay tool behind an opt-in
   flow registry; no stage workflow change yet.
2. Generate and check in the pilot `customer-address` flow with parameterized
   inputs; run it with one input set, then a second approved plan revision with
   different values and no spec change.
3. Add the `stage.replay` step to the `stage-test` family and route to it only
   when the plan declares a replay-eligible flow.
4. Add deterministic report mapping for a pilot plan with `expectationIds`;
   compare the generated report with the tester-authored report.
5. Add CI execution for one flow with an inputs file, then a suite that runs the
   same flow twice with different inputs or two independent read-only flows.
6. Make replay the default for eligible flows; keep `stage_run` and the
   stepwise browser path for gaps and failures. Roll back by disabling the
   `stage.replay` route; generated flows remain inert files.

## Open Questions

- **Stage-specific flows:** the manifest currently pins a stage. If the same flow
  should run on several stages with identical applications, allow a `stages`
  allow-list instead of a single id.
- **Trace retention:** keep the full trace only on failure, or also keep a
  success trace for a bounded number of runs? The recommendation is failure-only
  by default, configurable per flow.
- **Report knowledge:** replay reports start with no knowledge observations. If a
  block needs to record one, add `ctx.observe` to the replay fixture in a
  follow-up rather than overloading `ctx.step`.
