## Context

The dash Agents panel (`agentic-coding/src/tui/dash/App.tsx`, "Agents" `Panel`) renders each agent as a two-line row: role + status badge, then model plus verifier verdict/duration/cost. Its data comes from `DashboardData.agents` in `agentic-coding/src/tui/dash/data.ts`, which today carries only `role/status/model/cost`.

Telemetry flows one way: runtime bridges in `agent-definitions/bridges/` append JSONL envelopes to the workflow's `telemetry.jsonl` (via `HERDR_TELEMETRY_PATH`) and POST the same envelope to `OTEL_EXPORTER_OTLP_ENDPOINT/v1/logs`. The pi bridge emits a `runtime.usage` event per assistant message with `inputTokens/outputTokens/cost`. The dashboard aggregates usage with `costSummary()`/`costMessages()` in `data.ts`, but those functions filter on `event === "model_usage"` — an event name no bridge currently emits (only demo data uses it), so real pi-run costs never reach the panel. Bridges are embedded into `src/workflow/embedded.generated.ts` at build time; that file is regenerated by `bun run build` and must never be hand-edited.

Pi's message usage exposes cache read tokens and timing on the same lifecycle hook the bridge already subscribes to, so no new hooks are needed.

See proposal.md for motivation; specs define the observable behavior.

## Goals / Non-Goals

**Goals:**
- One compact metric line per agent: cost, tokens in/out, cache hit rate, run duration, tokens/s.
- All displayed metrics derived from telemetry events that also flow out through OTel — no second data path.
- Works for all runtimes by omitting unavailable fields rather than faking them.

**Non-Goals:**
- New modal/popup views or historical per-message drill-down for these metrics.
- Changes to the OTel receiver, trace viewer, or span schema (usage stays on the existing log envelope).
- Backfilling metrics for runs that produced no extended usage events.

## Decisions

1. **Extend the existing `runtime.usage` log event instead of new spans or metrics.**
   The bridge already exports this envelope to `/v1/logs`; adding `cacheReadTokens` (and writing duration/derived tokens/s) keeps a single schema and single export path. Alternatives considered: OTLP metrics instruments (heavier, duplicates the log pipeline, receiver changes) or per-turn spans (spans model operations, not scalar readings).

2. **Fix the `model_usage` vs `runtime.usage` mismatch at the aggregation layer.**
   `costSummary()`/`costMessages()` will accept both event names (`runtime.usage` normalized as the canonical name going forward). Renaming history or migrating old files is not worth it; both names cost one predicate. Demo fixtures move to `runtime.usage` for parity.

3. **Duration semantics: wall-clock per role from first to last telemetry event of the current run.**
   First `runtime.started` → latest `runtime.settled`/`runtime.usage` timestamp for the role, matching how `verifierTimeline` already derives duration. Tokens/s uses output tokens divided by summed per-message generation time when available, falling back to wall-clock duration. Wall-clock is approximate (agents idle between turns); documented as a trade-off rather than tracking active-time state machines.

4. **Cache hit rate = cache-read input tokens / total input tokens, computed at display time.**
   Raw counts stay in telemetry (so OTel consumers compute their own ratios); the dashboard derives the percentage when rendering. Avoids baking a derived value into the event schema.

5. **Panel layout: keep two-line rows, add one bounded metric line (three lines total per agent).**
   The third line packs `tok 12.3k→4.5k · 78% cached · 14m32s · 31 tok/s` next to the existing model text or replaces it when space is tight; truncation via the panel's existing `overflow="hidden"` boxes satisfies the bounded-rendering requirement without layout redesign. Cost stays where it is today.

6. **Bridge changes limited to `pi-telemetry.ts` initially.**
   Pi is the runtime used by this workflow's agents and the only bridge with a typed usage hook. OpenCode bridges emit generic lifecycle events without token detail; per spec they omit unsupported fields. Their envelope shape is unchanged, so they benefit automatically if their runtimes later expose usage.

## Risks / Trade-offs

- [Wall-clock duration overstates active time for long-idle persistent roles] → Label remains "duration for the run"; tokens/s prefers summed generation time so efficiency is not diluted by idle gaps.
- [Old telemetry.jsonl files lack the new fields] → Aggregation treats missing fields as absent and the panel omits them; nothing breaks on pre-change workflows.
- [Three-line rows reduce visible agents per panel height] → Metric line reuses muted styling and only renders when any metric exists; verifiers awaiting runs keep two lines.
- [Embedded bridge drift if `bun run build` is forgotten after editing `pi-telemetry.ts`] → Task list includes regeneration and a diff check on `embedded.generated.ts`.
- [OTLP endpoint receives larger envelopes] → Added fields are a few dozen bytes per message; well within the existing 750 ms fire-and-forget budget.

## Migration Plan

Purely additive: deploy by rebuilding (`bun run build`) and restarting the dash. Old telemetry files render with fewer metrics; no rollback concerns beyond reverting the commit.
