## 2. Execution semantics

- [x] 2.1 Port semantic tree versus execution-key deduplication with duplicate-dependency command-count tests.
  - `src/server/actions/coordinator.ts` ports the execution/claim coordinator and `src/server/actions/engine.ts` the runner's execution-key path: the key is scoped to the run (`<runId>:<executionKey>`), the canonical owner records its claim, and a second semantic node that reaches the same key emits `step.reference` carrying the canonical id and mirrors the canonical outcome. Claims come from the step configuration (`resourceClaims`), are sorted, released with the lease, and a conflict raises `ClaimConflict` naming the claim and its owner. `clearScope` makes a completed failure retryable.
  - Evidence: `test/actions-execution.test.ts` pins that two dependency paths execute the work once (handler called once, event sequence `started(root) → started(direct) → completed(direct) → reference(transitive) → completed(root)`), that exactly one command leaf is produced while the reference owns no command, and that the same key in a later run executes again.
- [x] 2.2 Port named typed value flow, scopes and visibility with secret/ephemeral serialization rejection tests.
  - `src/server/actions/values.ts` ports the per-run value store, `fmt.Sprint`-compatible rendering (endpoints as `protocol://host:port`, scalars, Go-shaped arrays and maps, `<nil>`) and `${key}` template resolution, which rejects an unclosed placeholder instead of passing it to a process. `definitionSnapshot` (task 1.4) is the serialization boundary: secret and ephemeral defaults and ports never reach a snapshot.
  - Evidence: `a value produced by one step reaches the next`, `a step consuming an absent value fails with the Go diagnostic`, `value templates render endpoints, scalars and Go-shaped containers`, `a secret value is delivered to its consumer but never serialized` (asserted end to end: the consumer sees the sentinel, the run tree never contains it) and the task 1.4 redaction tests.
- [x] 2.3 Port run/step/command accounting preserving one leaf per executed command and commandless composites/SDK steps.
  - `src/server/actions/command.ts` gives every executed command exactly one step, one runner invocation and the derived identity `<stepId>-command-0`, with `command.started`/`command.output`/`command.completed|failed` as its only events. `src/server/actions/projection.ts` turns those events plus the step lifecycle into the run tree; a composite or an operation step stays commandless.
  - Evidence: `a composite that runs no command produces no command record`, `the command identity is derived from the step, exactly once`, `a step after a failure emits no command event and no command leaf` (a real `sh -c` failure: no placeholder step, no command for the skipped step), and the task 1.4 projection tests.
- [x] 2.4 Port executor failure propagation and always-run cleanup behavior.
  - The composite rule is one place in `engine.ts`: `always-run` and `always` children run after a failure, `on-failure` children run only after one, everything else is skipped; a failed child without an error still fails the composite with `child step failed`; a cancelled signal stops children before they start but never a cleanup step; a throwing handler fails its step instead of the engine.
  - Evidence: `a failure stops normal steps and runs an always-run cleanup`, `an on-failure step runs only after a failure`, `a child failure without an error still fails the composite`, `cancellation stops normal steps but lets cleanup run`, `a missing handler fails the step instead of silently succeeding`, `a handler that throws fails its step without failing the engine`, plus the real-process failure path in task 2.3.
- [x] 2.5 Port coordinator/resource leases, cancellation and late-result ownership rejection.
  - A lease publishes at most once and only as owner: a non-owner release is dropped, a second owner release is ignored, a cancelled wait rejects instead of hanging, and a lease's claims are released with it.
  - Evidence: `a shared lease waits for and mirrors the canonical result`, `a completed failure is retried once its scope is cleared`, `a non-owner release is dropped, so a late result cannot publish`, `only the first release of an owner publishes`, `a cancelled wait rejects instead of hanging`, `claims are ordered and released with the lease`, `resource claims come from the step configuration`.
- [x] 2.6 Port readiness gates and explicit already-running outcomes without invented command steps.
  - `src/server/actions/readiness.ts` ports the readiness step and probe factory (tcp, http, container health, compose, kubernetes pods, process survival, stabilization delay) and `src/server/actions/process.ts` the managed-process handler that survives the action context. A probe that never becomes ready fails the action; an already-running resource completes the step with the `already-running` outcome and no command event; a probe that cannot even be constructed (missing runtime or process handle) fails instead of hanging.
  - Evidence: `a process that exits before readiness fails the action` (end to end through the engine), `an already-running resource succeeds with no command step` (outcome + empty command list), the probe suite (survival window, tmux pane, tcp/http, container polling, compose non-running/all-running, podman `--all`, pod selection, retry-until-cancelled), and `a managed process outlives the action context and dies with the store`.

- [x] 3.3 Implement process spawning/output/exit/error and process-group cancellation with platform fixtures.
  - Spawning, streamed output, exit codes and error text landed in task 2.3 (`command.ts`, `process.ts`). - [x] 3.4 Port tmux/script readiness, long-lived process recovery and frontend terminal-launch coordination.

Terminal-launch coordination: `writeShellActionScript` writes the script with the `# devenv:name=` / `# devenv:mode=` header a launch consumes, and `parseShellScriptMetadata` reads it back so a `run` action resolves to a tmux window and a build/test action to logged output — no launcher behaviour is invented server-side, the frontend request carries the capability.
