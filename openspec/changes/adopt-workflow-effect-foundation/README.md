# Full workflow Effect migration

Primary proposal: `adopt-workflow-effect-foundation`. The other three changes are follow-up proposals, not implementation tasks implicitly included in the primary change. All four must land before the migration is called complete.

## Motivation and end state

Primary leverage: make workflow changes easier for coding agents by replacing repository-specific orchestration conventions with a small, documented set of Effect patterns. This is a project goal, not a claim that every model is inherently better at Effect. Validate it with representative tasks and record contrary evidence.

Full migration means all workflow application operations and runtime I/O use Effect: contracts, typed operational errors, store access, startup/configuration, evidence collection, outbox execution, adapters, credentials, wiki I/O, telemetry, CLI, and workflow-facing dashboard integration. Pure graph/step/projection/formatting functions remain plain deterministic TypeScript. Bun/FFI and third-party Promise APIs remain implementation details of named boundary adapters, not a second orchestration style.

Keep the SQLite store, outbox, workflow identities, semantic pins, authorization rules, and external CLI/JSON protocols. This is not replacement with `@effect/workflow`, a cluster service, or a new durable store. Core Effect does not supply crash recovery or exactly-once external actions. Unrelated TUI features and standalone tools are outside scope.

## Existing proposal dependencies

- `version-workflow-store-migrations` must land before phase 2. Its schema initialization and compatibility contract remain authoritative; inspect current work rather than replacing it.
- `separate-workflow-observation-execution` must land before phase 2. It owns explicit drain, scheduling semantics, non-mutating reads, and secure asynchronous evidence preparation. Phases 2–4 migrate that behavior to Effect, not introduce a competing coordinator.
- `centralize-step-completion-behavior` must land before phase 2. It owns moving completion decisions to pure step behavior. Effect does not introduce another step interface.
- `split-dashboard-responsibilities` and `enforce-source-layer-boundaries` must land before phase 4. Reuse their modules and graph checker instead of creating alternatives.
- Existing prerequisites of those proposals still apply. Completed/archived prerequisites do not need to be repeated. Dependencies are explicit planning gates; OpenSpec does not automatically schedule these changes.

If implementation order changes, revise the affected proposals together before implementing overlapping files. Do not silently supersede an active proposal or duplicate its work.

## Completion gates

Each phase leaves working callers and focused regression checks. Temporary compatibility bridges are listed in `agentic-coding/docs/workflow-effect-migration.md` with exact symbol, caller, owner phase, and removal check; phase 4 removes every migration-only bridge. Stable boundary adapters and pure identity descriptors are not migration shims.

Implementation workers run focused checks, type checking, Biome with zero diagnostics, and relevant build checks. Workflow-owned test verification runs the full configured suite. Generated workflow assets are regenerated by `bun run build`, never hand-edited.

Compare the same two representative agent tasks before and after: add a handler with one transient failure and cancellation; extend a validated command and its pure step behavior. Record model/version, available instructions, prompts, checks, human corrections, and review findings. Improvement is evaluated through observed results, not a fabricated productivity percentage. Correctness and compatibility remain mandatory regardless of productivity results.
