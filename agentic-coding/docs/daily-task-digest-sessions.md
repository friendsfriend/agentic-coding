# Named workflowless sessions and the daily task digest

## Lifecycle and custody

Pi Durable sidebar entries are independent named **workflowless** native conversations, not workflows and not Home/Orchestrator. Selecting an entry reopens its exact persisted identity with the existing transcript renderer. Background delivery does not navigate or change active selection. `/new` explicitly creates a separate coding session; it does not replace the digest destination. Automatic names carry a retry-stable creation discriminator. Pin metadata and the transcript header show the immutable session ID prefix, so even duplicate or clipped explicit names remain distinguishable.

The metadata-only `<config>/pi-durable/sessions.json` registry stores version, immutable session/creation-operation IDs, OS-user custody, display name, pinned cwd/model/thinking/tool policy/source roots, active selection, exact native store/conversation binding and deletion tombstones. Native pi-durable remains the only transcript store. A private atomic write under the existing process-released secure file lock prevents concurrent overwrite and stale lock ownership. Native history is never copied into this registry.

On the first open, legacy `session.json` is adopted under a stable legacy receipt. Its existing native conversation is looked up without creating one. Missing/corrupt/future metadata, changed native identity, foreign custody, deleted identities and missing legacy conversations fail closed; they are not an invitation to erase metadata or create replacements. Orphan temporary files are not authoritative. Explicit create persists the operation identity before native host I/O, then binds the native conversation exactly. Retrying the same operation with changed settings is rejected. Deletion first durably revokes native scheduled admission in the same per-conversation serialization boundary used by activation, then tombstones metadata and retains native history. A deletion is not acknowledged if native revocation cannot be confirmed; retry through the supported command. Once acknowledged, a scheduler that captured the old binding cannot enqueue new work, including after host restart. Deletion does not retarget schedules or imply cancellation of a turn admitted before the revocation fence.

## Supported setup (no schedule activation)

Use the supported command, not manual JSON edits. Choose a **real configured** provider/model and an existing git repository/base branch. Enable codemode in the user's global pi configuration (`defaultTools: ["+codemode"]`) and configure source MCP integrations there. No credentials belong in task text or scheduler JSON. Integration secrets stay in the existing credential/configuration facilities.

```sh
agentic-coding session create \
  --name 'Daily task digest' \
  --cwd /absolute/path/to/an/existing/git/repository \
  --model configured-provider/configured-model \
  --thinking low \
  --operation-id daily-task-digest-initial-setup \
  --collection \
  --gitlab-hosts gitlab.your-company.example \
  --gitlab-tool-host gitlab.your-company.example \
  --repository-roots /absolute/path/to/configured/workspaces
agentic-coding session list
agentic-coding session digest-proposal EXACT_SESSION_ID --base-branch main
```

The paths, host, model and ID above are deliberate placeholders: replace them with actual configured local values. `create` validates model availability and pins explicit settings; it creates a native session but **does not submit a model turn or create a schedule**. It is background by default; `--select` is an explicit user selection. Multiple repository roots/hosts are comma-separated; use actual trusted roots, never `/`. Retry the same creation operation ID after an interrupted setup. `list` supplies exact immutable IDs and bindings. `select ID` changes selection; `delete ID` tombstones it. The sidebar refreshes metadata without navigating.

`digest-proposal` is a pure, nonactivated proposal containing a self-contained job, calendar timing, late policy and confirmation checklist. It makes no source calls, starts no host, and writes no scheduler state. It requires a bound collection session with explicit model/thinking. Before eventual use, validate repository/baseBranch, model, source availability, exact destination and preview using the existing authenticated scheduling API/manual client. The authenticated operator and orchestrator may create or mutate read-only session-targeted jobs/schedules. Writable standalone execution approval and manual destination initialization remain operator-only; session custody, pinned identity and dispatch validation are unchanged. There is intentionally no new scheduler or automatic live activation in this feature.

## Calendar and policy confirmation

The proposed timing is calendar Monday–Friday, 09:00, `Europe/Berlin`, using the existing DST-aware calendar engine (09:00 CET = 08:00 UTC; 09:00 CEST = 07:00 UTC). Each occurrence uses **[nominalDue − 24h, nominalDue)**, even on Monday and even if actually executed late. Monday does not mean “since Friday”; weekend activity earlier than that window is omitted.

The proposal uses existing `run-late`. The alternative is `expire-after` with `graceMs: 21600000` (six hours): an occurrence older than the grace expires instead of executing. Neither option widens its evidence window. Existing scheduler catch-up/coalescing and per-job no-overlap remain unchanged: an outstanding occurrence can cause a later slot to be marked skipped-overlap, not a simultaneous second digest. **Confirm Monday coverage, run-late versus six-hour expiry, and no-overlap/catch-up behavior with the developer before creating any live recurring schedule.** No such live schedule was created during implementation.

## Security and source coverage

The `collection` tool policy is a host-enforced selection, not just prompt text. It has no shell, arbitrary filesystem read/write/edit, workflow management, scheduling, remediation or operator/environment tools. `digest_repositories` is a narrow read-only native tool using pinned roots/hosts; no path argument is accepted. Repository enumeration has depth/directory budgets, skips symlinks, never fetches/checks out, canonicalizes SSH/HTTPS/nested namespaces, and returns deduplicated actual GitLab identities plus diagnostics. Arbitrary paths/projects cannot be smuggled through direct or nested GitLab calls: the bridge rechecks discovered local project membership and the pinned integration-host binding at execution time. `--gitlab-tool-host` is the operator's explicit binding of the configured GitLab integration to its real host; verify it against integration configuration. No binding means no GitLab calls, and remotes on other hosts remain unavailable rather than being queried against a same-path project on the wrong host.

Imported tools use an explicit reviewed read allowlist, independent of the existing generic read-only profile's machine allow rules. The same execution gate applies to direct and nested/codemode calls. Wiz's generic dispatcher additionally checks the **inner method**, not just the outer tool name: mutation/remediation and unknown list methods are denied. Existing Home, workflow, review, login and ordinary native-bridge policies are not relaxed. Session host children strip workflow/environment operator capability variables.

The version-3 stored task starts with `digest_collection_plan`: compiled all-accessible-project Jira discovery, per-method Wiz bounds and all-state unfiltered GitLab search parameters from the **native scheduled occurrence**, not dates parsed from source/model text. Jira discovery is widened one calendar day because the connector does not advertise its query timezone; late discovery is not upper-bounded by nominal due. Only actual timestamped events in the exact nominal window qualify. Restrictive or otherwise unverified queries cannot certify full scope coverage.

Jira/Wiz/GitLab invocation and pagination remain model-directed, but the host bridge automatically records **actual executions**, provider errors, candidates, expected detail/comment/domain/project scopes and continuations. Advisory `normalize_digest_source_page` calls and model-authored events/success rows do not certify reads. The native renderer uses those execution receipts, not reconstructed model events; missing or failed scopes cannot vanish. Missing Jira/Wiz/GitLab/Azure Monitor/New Relic coverage is unavailable, never empty success. Recorded page/item/dispatch-attempt/failure counts override model claims, including zero counts for unobserved scopes. Receipts/production caches are process-local and bound to occurrence, conversation and trusted settings generation, not a second durable report store: after recovery without observed reads, fresh collection is needed or coverage stays incomplete. An already committed native answer remains associated with its original receipt and is not regenerated.

Budgets are 1,000 source reads per native occurrence; 100 pages/10,000 inspected records per source/scope; 2,000 emitted events overall. Each normalization page inspects at most 1,000 top-level rows and 4,000 nested history/change/comment entries. Out-of-window and irrelevant records still consume inspection budgets. Provider failures, unsupported Markdown/JSON, cursor loops, unfinished pages and caps remain explicit. Native delivery success is independent of report completeness; these adapters do not guarantee that each external provider exposes all relevant history.

- **Jira:** all accessible projects, including unassigned work. Creation, actual history transitions and comment timestamps are evidence. `updated` is only a candidate discovery hint; history unavailable means explicitly unknown movement, never an inferred transition. Missing changelog/comment pagination capability is a coverage gap.
- **Wiz:** currently reviewed dispatcher reads are `list_issues`, `list_posture_issues` and `list_attack_surface_findings`. Discovery is metadata-only; new findings must have creation/first-seen timestamps in the window. Posture includes vulnerability/secret/data types; attack surface covers its supported finding types. Other discovered domains/methods remain visibly unavailable until their execution policy is reviewed. No live findings were queried during implementation.
- **GitLab:** only actual remotes under configured roots/approved hosts; duplicate clones do not multiply MRs. Ordinary creation, actual merge timestamps, timestamped discussion/review notes and failed head pipelines with `finished_at` qualify, including new activity on old MRs. Notes are not inferred approvals; an `updated_at` is unverified activity, not evidence of a change/review/failure. Verified Renovate creation is a highlighted subset requiring returned authenticated bot metadata and specific identity, never title/branch heuristics. The advertised search does not expose a reviewed paginated/date-filtered activity-history API, so complete review/change/pipeline history and pagination remain explicit gaps, not invented endpoints.

The observed Jira transport uses `Found N issue(s) on this page (more available):`, optional `Next page token:`, and `- **KEY-N**: title` rows. These are candidates, not timestamped events. The actual Markdown detail omits creation/update/history/link fields even when requested: report those capabilities unavailable. Actual comments use `N comment(s) on KEY-N (showing START–END):`, `--- Comment N ---`, then `[id:ID] Author @ ISO_TIMESTAMP:`; only that metadata is retained, never bodies. The adapter follows actual offsets, rejects count/header ambiguity (including forged body headers), and never invents history or source URLs. JSON history is consumed only when actually returned; no separate history tool has been established. A fixture with 428 candidates proves that unread detail/comment scopes remain incomplete, not that 428 live issues were fully collected.

### Verified production telemetry (operator configuration required)

`productionSources` in the trusted collection-settings JSON accepts at most one entry per `provider` (`azure-monitor` or `new-relic`), literal `environment: "production"`, the verified `environmentField` (`environment`, `deployment.environment` or `deployment.environment.name`)/`environmentValue` (known QA/dev/test/staging values are rejected), exact `services`, and a nonsecret trusted-config `provenance` reference. Obtain these values from actual deployment/integration configuration; placeholders, source text, error messages, account-wide discovery or guessing service names are not verification. Do not put credentials, endpoints, queries or response paths in these settings. Missing selectors/provenance yield unavailable without a query; no actual production selectors or GitLab integration host were established by implementation.

`collect_digest_production_logs({})` compiles read-only Azure `AppExceptions` and New Relic `TransactionError` service/signature aggregates for the exact nominal window. Azure's outer relative API timespan widens for late execution while the KQL predicate remains the nominal 24 hours. QA or foreign services are rejected. Only exact reviewed provider bindings may run; generic telemetry tools and result-file readers remain denied even through codemode. The host privately consumes the actual provider-specific Markdown/structured receipt and its exact returned NDJSON file in 1-based pages of 200, at most 1,000 groups/provider, with a ten-second per-read deadline. Arbitrary, duplicate, cross-provider, cross-conversation or cross-occurrence paths cannot be supplied by a model/source. A previously observed path cannot be rebound to a different conversation, occurrence or trusted settings generation. No receipt/path is returned as tool authority. Count/row caps are disclosed, previous successful rows survive later failures, and provider counts are never summed across platforms. Missing evidence deep links remain partial coverage: provider portals are not substitutes. New Relic null/empty error classes enter an explicitly unclassified bucket with a context gap rather than disappearing through null facets. Counts describe captured source events, not unique incidents or customer impact; provider retention/sampling is not independently verified. These narrow tables do not claim complete infrastructure/log/alert coverage.

Reports lead with evidence-supported prioritized next actions, workload by source, and required-source coverage, then Important / Relevant / Minor with factual reason, link and next action. No causal/customer-impact relationship is inferred across providers. Wiz grouping requires known resource scope, exposure and status and preserves title, domain, resource scope, status, exposure and severity distinctions; missing context leaves separate findings rather than merging unrelated risks. Production signatures remain separate by provider/service. At most ten member identities/group, 2,000 final events, 32,000 item-detail bytes and 14,000 coverage-detail bytes are projected. Omitted member identities, metadata or scope details produce an explicit cap notice and structured incomplete verdict, never an oversized purportedly complete report. `render_daily_digest` returns `reportCoverage` independently of scheduler delivery status; its bounded scope samples include the total incomplete-scope count. Links, Markdown/control characters and credential-like values are sanitized. Missing fields, inaccessible data and all-source failures stay diagnostic; “no verified items in covered results” is not “the inaccessible source was empty.”

## Existing deployment: guarded post-merge operator procedure

Preserve session `f440fdc0-4e0b-4920-bba3-ca854a6eade7`, job `3d6a2361-09a7-4eff-89ff-d18eb23fd80f` and schedule `214247ce-cde0-49a2-9909-bf63aed70e45`. A new task constant does not update a stored job. Do not recreate entities, retry creation with changed settings, patch registries/native history or use a replacement destination. This implementation changes repository code only, not those live entities.

After review/merge/rebuild, Home/operator—not the worker—must:

1. Pause the existing schedule through the authenticated scheduler, drain/reconcile nonterminal occurrences and confirm no admitted/queued/active turn. Export the current stored job/revision, all affected schedules and prior collection settings for rollback. Verify exact session/owner/native host/conversation/cwd/model/thinking and real GitLab integration binding. Establish production selectors/provenance from trusted configuration; absent facts stay unconfigured.
2. Prepare a private settings JSON with only `gitlabHosts`, optional `gitlabToolHost`, `repositoryRoots`, `productionSources`. Preview without starting a host or changing selection:
   `agentic-coding session digest-settings-preview SESSION_ID --settings SETTINGS_FILE`.
   Review full prior/proposed settings, exact binding and expected SHA-256 metadata revision.
3. With the existing exact collection run already open and idle, use
   `agentic-coding session digest-settings-apply SESSION_ID --settings SETTINGS_FILE --expected-revision SHA256`.
   This requires its existing native host; it never spawns/replaces one. If unavailable, reopen the exact existing pin through the normal native session surface, not by creating another session. Host-side ownership/revocation, admission and idle guards run in the same conversation-keyed serialization boundary as reserve/activate/delete. Authorized pending admissions—including pre-enqueue crash windows—block replacement. Source settings/collection revision are narrowly mutable; binding, creation identity, model/thinking/tool policy/cwd/history and active selection are preserved. Recovery overlays persisted settings rather than stale `run.env`.
4. Generate the nonactivated stored-job request and actual settings diff:
   `agentic-coding session digest-job-update-proposal SESSION_ID --job STORED_JOB_FILE --schedule SCHEDULE_ID --settings SETTINGS_FILE`.
   It emits a version-3 `jobs.update` request with expected job revision, affected schedule, exact preserved target, and collection-settings expected revision. It does not update settings/job or activate anything. Reload all affected schedule IDs and replace/review that list if the job is shared. Apply/preview only through the existing authenticated scheduling update facilities; writable approval/admission is not conferred by this artifact.
5. Preview calendar/history/destination and confirm unchanged weekdays 09:00 `Europe/Berlin`, run-late, nominal preceding 24h including Monday, no-overlap and background/no-focus-steal operation; resume only after both guarded updates succeed. Verify coverage separately from delivery. If either update fails, remain paused, reload revisions and reassess—never create duplicates as a workaround.

Rollback while paused/drained: preview/apply the exported prior settings using a **fresh** metadata revision, then restore the prior task/job through authenticated `jobs.update` with its current expected revision and affected schedules. Re-preview the unchanged schedule/destination before resuming; never roll back by deleting native history. No live application/restart/acceptance was performed here. The dedicated wiki step should amend the existing concept's JSON-only, Renovate-only and delivery-equals-coverage claims; describe the host-only production capability, actual-read limits and this operator procedure without claiming globally complete or already configured production coverage.

## Admission and verification

A read-only standalone target can carry `destination.kind: workflowless-session` plus exact session/owner/native-store/conversation IDs. Repository/baseBranch/model/thinking remain pinned. This route uses the existing scheduling store, reservation/admission/fences, native request-id receipts, calendar/history/pause/cancel controls and per-job no-overlap; it never creates occurrence-specific worktrees or a workflow for the digest. Every dispatch revalidates metadata/custody/settings, recovers only that session with `select:false`, and uses the existing native scheduled-admission envelope. Missing or replaced destinations fail rather than falling back to the currently focused session. Repository/base validation has a five-second subprocess deadline and kills/reaps its own child on timeout/cancellation, reported as retryable infrastructure failure. Scheduling API mutations recheck referenced job revisions inside the committing transaction after asynchronous validation, including both old and new job references when retargeting a schedule.

Native submission receipts persist input/answer entry IDs and scheduler result association. Repeated activation uses the same occurrence request ID; querying the receipt reads that answer, not the latest unrelated assistant message. Busy-host barriers remain controlled by existing native admission/reconciliation; this adapter does not interrupt unrelated work or choose a replacement host. No parallel transcript or report store is introduced.

Focused fixtures cover metadata integrity/retry/custody/tombstones, evidence windows/coverage/pagination, remote identity discovery, scheduler routing/restart/native receipts, visible native report projection, and direct/nested read-only MCP enforcement using fake providers/models and isolated stores. Rendered App acceptance composes the real authenticated SchedulingApi, SchedulingService/Store and exact session adapter with an on-disk fake-model DurableHost and loopback synthetic MCP. It ticks a synthetic occurrence, discovers/reads two pages through codemode, passes actual responses through production normalization/rendering, loses an activation acknowledgement, restarts both native host and scheduler store, and reconciles the one original answer receipt without repeating collection. The rendered App remains on Home until explicitly opening the named pin, switches/reopens retained reports, and creates/reopens two distinguishable `/new` sessions; duplicate explicit pin names have separate rendered coverage. Abort, shutdown and deletion race fixtures exercise the native mutation/revocation boundaries. All fixtures isolate HOME/config/pi/wiki/stores; native transport seams are in-process and only the synthetic MCP uses loopback HTTP. This is not a claim of live-account completeness or manual live-TUI acceptance; neither live collection nor schedule activation is required or performed by these fixtures.
